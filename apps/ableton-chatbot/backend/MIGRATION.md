# Moving off SQLite-on-EFS: why, what changed, and what's left

## Why

`beatmind-api` runs as a single Fargate task (`desiredCount=1`) with `minimumHealthyPercent=0`, so
every deploy has a real gap — the old task fully stops before the new one starts — currently
measured at ~132 seconds with zero healthy backend targets. That's deliberate, not an oversight:
`/data/musai.db` is SQLite on an EFS (NFS) volume, and SQLite's file locking is well known to be
unreliable over NFS, so the service is kept to one writer at a time rather than risk two Fargate
tasks touching the file together.

A true zero-downtime rolling deploy (`minimumHealthyPercent=100`, `maximumPercent=200`, briefly two
tasks running together) is only safe once the datastore itself handles concurrent connections
correctly — which is what a real database server does and a bare file does not. That's the reason
for Postgres, not performance or scale.

## What changed

`database.py` now supports two backends, selected by `DB_BACKEND` (`sqlite`, today's default, or
`postgres`) and `DATABASE_URL`. Every other file in the backend still calls `conn.execute(sql,
params)` directly on the connection and reads rows by name or position, exactly like `sqlite3`
allows — `database.py`'s `_PGConnection`/`_PGCursor` reproduce that surface on top of psycopg2
(`DictCursor`, so `row["col"]` and `row[0]` both work; `?` placeholders translated to `%s`), so
none of that calling code needed to change.

What genuinely needed per-backend handling, because SQLite and Postgres disagree on syntax or
semantics (all in `database.py`, `billing.py`, `security.py`, `ai_usage.py`, `product_updates.py`,
`stripe_routes.py` — search for `is_postgres()`):

- `AUTOINCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` (`database.autoincrement_pk()`). **BY
  DEFAULT, not ALWAYS** — SQLite's AUTOINCREMENT accepts an explicit id if the INSERT provides
  one; a test fixture relies on exactly that to seed a well-known row.
- `datetime('now')` → `NOW()` (`database.now_sql()`).
- `PRAGMA journal_mode` / `PRAGMA table_info` → skipped / `information_schema.columns` — both
  SQLite-only; Postgres's durability is the server's own job.
- `INSERT OR IGNORE` → `INSERT ... ON CONFLICT (...) DO NOTHING`. This syntax is itself portable —
  SQLite has supported it since 3.24 — so these became dialect-*neutral*, not dialect-branched.
- `cursor.lastrowid` (one call site, `create_user`) → `INSERT ... RETURNING *`, also portable on
  both (SQLite since 3.35), and an improvement even for SQLite: one round trip instead of two.
- `BEGIN IMMEDIATE` (3 call sites: `billing.charge`, `billing.refund`,
  `stripe_routes.apply_subscription`) — SQLite's whole-database writer lock, used today to
  serialize a check-then-act race. No Postgres equivalent exists, because Postgres doesn't need
  one: a `SELECT ... FOR UPDATE` on just the specific row in question is the correct, more
  granular replacement, applied only on the Postgres path. SQLite keeps `BEGIN IMMEDIATE`
  unchanged.
- One real, worth-flagging-for-future-dialects bug caught by testing: `SUM(rate_basis =
  'placeholder')` relies on SQLite treating a boolean comparison as 0/1; Postgres's `SUM` doesn't
  accept a boolean argument at all. Fixed with an explicit `CASE WHEN ... THEN 1 ELSE 0 END` —
  portable on both, and arguably clearer regardless of backend.
- Similarly, `COALESCE(request_id, id)` mixed a TEXT column with an INTEGER column — SQLite
  coerces freely, Postgres's `COALESCE` requires the same type. Fixed with an explicit
  `CAST(id AS TEXT)`.

## How this was verified

The whole backend test suite (`tests/`) was run against a real local Postgres (`docker run ...
postgres:16-alpine`), not just reasoned about:

```sh
docker run -d --name beatmind-pg-test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=beatmind \
  -p 55432:5432 postgres:16-alpine

python3 -m pytest tests/                                                            # sqlite (default)
DB_BACKEND=postgres DATABASE_URL=postgresql://postgres:test@127.0.0.1:55432/beatmind \
  python3 -m pytest tests/                                                          # postgres
```

Both runs: 439 passed / 29 failed / (postgres: 5 skipped). The 29 failures are identical on both
backends and pre-existing — unrelated to this change (a `stripe.checkout` test-isolation issue that
reproduces identically with zero Postgres code involved at all; confirmed by running
`test_billing.py` alone, repeatedly, under SQLite only, with no env changes). The 5 skips
(`tests/test_database.py`'s four `DatabaseTests` and `tests/test_billing.py`'s
`MigrationTests::test_startup_adds_plan_columns_to_an_existing_database_without_losing_rows`) are
`@unittest.skipIf(database.is_postgres(), ...)`: they test SQLite's own journal-mode/PRAGMA
behavior and a raw-sqlite3 migration fixture, which have no Postgres equivalent to test.

`tests/conftest.py`'s `isolated_database` fixture reads the real `DB_BACKEND`/`DATABASE_URL` env
vars (not a separate test-only variable) so `@unittest.skipIf(database.is_postgres(), ...)`
decorators — evaluated by `unittest` at class-body/import time, before any fixture runs — see the
correct value. It resets the Postgres schema (`DROP SCHEMA public CASCADE`) at the start of each
run, matching SQLite's brand-new-temp-file guarantee, and clears `security.py`'s own
"already issued CREATE TABLE" cache (`_token_tables_ready`) between phases.

A fixture *parametrized* per backend would run both in one `pytest` invocation instead of two, but
pytest cannot inject a parametrized fixture into this suite's many `unittest.TestCase`-based tests
— hence the two-invocation form above.

## What's NOT done yet (this file covers the code only)

1. **Provision real RDS Postgres** in the same VPC/subnets as the ECS service.
2. **Migrate the live SQLite file's actual data** (`/data/musai.db` on the production EFS volume)
   into it — real signups exist already, pre-launch; this needs a verified row-count/spot-check
   migration, not a fresh empty database.
3. **Cut the live ECS task over** to `DB_BACKEND=postgres` + `DATABASE_URL`, first under *today's*
   deployment config (`minimumHealthyPercent=0`) as a zero-added-risk check that the app behaves
   correctly against Postgres in production before changing anything else.
4. Only after (3) is proven stable: flip `minimumHealthyPercent=100`, `maximumPercent=200`, and run
   one supervised test deploy (pre-launch, not during real traffic) to directly confirm a true
   zero-gap swap.

Steps 2 and 3 touch real production data and the live service; do these deliberately, not as a
continuation of a long automated run.
