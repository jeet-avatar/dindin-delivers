# ArthaBuild Incident Response Runbook

**Version:** 1.0
**Date:** 2026-04-10
**Contact:** support@techcloudpro.com

This is a lightweight runbook for a startup-stage product with a small team.
For formal SOC2 Type II, a full escalation matrix will replace this document.

## Severity Tiers

| Tier | Definition | Response SLA |
|------|-----------|-------------|
| P1 | Data breach — customer NetSuite data or credentials exposed | 1 hour containment; 72-hour customer notification (GDPR baseline) |
| P2 | Service compromise — unauthorized access to ArthaBuild admin/user accounts | 4 hours |
| P3 | Vulnerability discovered — no evidence of exploitation | 5 business days |

## 5-Step Response Process

### Step 1 — Detect
- Sources: Customer report, security scan alert, log anomaly
- Log the incident: date/time, reporter, initial description, severity tier assignment
- Preserve evidence: DO NOT delete logs, containers, or DB snapshots before investigation

### Step 2 — Contain
- P1/P2: Immediately rotate `JWT_SECRET_KEY` (invalidates ALL active sessions across deployment)
- P1: Snapshot the ArthaBuild SQLite DB + audit logs before any changes
- P2: Force-logout specific accounts via JTI blacklist if available
- P3: No immediate containment required — assess scope first

### Step 3 — Assess
- Review AuditLog (`GET /api/admin/audit`) for timeline of suspicious events
- Check: which accounts were accessed, what actions were taken, what data was reachable
- Determine: exploit path, affected resources, scope of exposure

### Step 4 — Notify
- P1: Notify affected customer(s) within 72 hours of confirmation (GDPR baseline)
  - What to include: date of breach, nature of data, actions taken, recommended steps
  - Channel: Email to customer admin contact on file
- P2: Notify customer admin within 24 hours
- P3: No customer notification required unless data was accessed

### Step 5 — Recover
- Rotate all secrets: `JWT_SECRET_KEY`, `SMTP_PASSWORD`, any other exposed credentials
- Patch the vulnerability (follow standard GSD workflow)
- Re-run security scan (pip-audit + ZAP) after patch
- Write post-mortem: root cause, timeline, fix, prevention measures
- Update `docs/security/SECURITY_CONTROLS.md` if a control needs strengthening

## Evidence Preservation Note
Before any remediation, preserve:
- `arthaBuild.db` snapshot (contains AuditLog)
- Container logs (`docker logs arthaBuild-backend-1`)
- Any relevant network access logs (CloudWatch if on AWS)
```

# ArthaBuild Data Classification

**Version:** 1.0
**Date:** 2026-04-10

## Data Inventory

| Data Type | Sensitivity | Location | Retention | Deletion |
|-----------|-------------|----------|-----------|---------|
| User email + password hash | HIGH | SQLite (`users` table) | Until user account deleted | `DELETE FROM users WHERE id=?` |
| JWT tokens | HIGH | Memory only (never persisted) | 24h (access) / 7d (refresh) | Automatic expiry; `JTI_blacklist` on logout |
| NetSuite TBA credentials | CRITICAL | Server RAM only (`session_store.py`) | Duration of session only | Wiped on logout/expiry/server restart |
| Audit log entries | MEDIUM | SQLite (`audit_logs` table) | Indefinite (SOC2 evidence) | No scheduled deletion; manual if legally required |
| Chat session history | MEDIUM | SQLite (`chat_messages` table) | Until user deletes session | `DELETE FROM chat_messages WHERE session_id=?` |
| Password reset tokens | HIGH | SQLite (hashed SHA-256 only) | 15 minutes | Auto-expired; deleted on use |
| Email verification tokens | HIGH | SQLite | 24 hours | Auto-expired; deleted on use |
| SuiteScript files generated | LOW | Filesystem (`TestSDFProject/`) | Until customer clears deployment | Files on EC2 EBS volume |
| License validation cache | LOW | SQLite (`license_cache`) | 7 days rolling | Auto-overwritten on re-validation |

## Data That NEVER Leaves Customer Infrastructure
ArthaBuild is a BYOC (Bring Your Own Cloud) product. The following data types never leave
the customer's AWS VPC:
- NetSuite TBA credentials
- Chat messages / prompts
- SuiteScript code generated
- FAISS vectorstore queries
- User accounts and audit logs

The only external communication is the license validation ping (license key + instance ID) to
TechCloudPro's license server. No customer data, prompts, or NetSuite information is included.

## Deletion Procedures
- **Single user deletion**: `DELETE /api/admin/users/{id}` (soft-delete, marks `is_active=false`)
- **Full data wipe**: `docker-compose down -v` removes all Docker volumes including SQLite DB
- **Audit log preservation**: Audit logs are retained even after user deletion (actor stored as string, not FK)

# ArthaBuild Secure Deployment Guide

**Version:** 1.0
**Date:** 2026-04-10
**Audience:** ArthaBuild administrators deploying to AWS

## Pre-Deployment Checklist

### Required Environment Variables
Set in `.env` before `docker-compose up`:

- [ ] `JWT_SECRET_KEY` — min 32 random characters (use `openssl rand -hex 32`)
- [ ] `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` — email for password reset
- [ ] `ALLOWED_ORIGINS` — your domain(s), comma-separated (e.g. `https://arthaBuild.yourcompany.com`)

### Network Configuration
- [ ] Deploy inside a private VPC subnet — no public internet access to port 8000 (FastAPI) or 11434 (Ollama)
- [ ] Only ports 80 and 443 exposed to internet (via Nginx)
- [ ] AWS Security Group: inbound 443 from 0.0.0.0/0; inbound 22 from your IP only

### TLS / HTTPS Setup (Production)
- [ ] Obtain TLS certificate (Let's Encrypt via Certbot, or AWS ACM)
- [ ] Place `cert.pem` and `key.pem` in `/etc/nginx/ssl/` on the EC2 instance
- [ ] Use **`nginx/nginx.prod.conf`** (not `nginx/nginx.conf`) in production Docker Compose:
  ```yaml
  services:
    nginx:
      volumes:
        - ./nginx/nginx.prod.conf:/etc/nginx/nginx.conf:ro
        - /etc/nginx/ssl:/etc/nginx/ssl:ro
  ```
- [ ] Verify HTTPS is working: `curl -I https://your-domain.com/` — expect 200 with HSTS header

### EBS Encryption
- [ ] Confirm `encrypted = true` in `infra/terraform/main.tf` before `terraform apply`
- [ ] EBS encryption applies to new volumes only — existing unencrypted volumes require snapshot-and-replace
- [ ] AWS KMS default key (aws/ebs alias) is used automatically — no additional IAM configuration needed

### Post-Deployment Security Checks
- [ ] `GET /health` returns `{ "status": "ok" }` (backend healthy)
- [ ] Login with first user (admin) — verify session works
- [ ] `GET /api/admin/audit` returns empty array (confirms audit log table created)
- [ ] Run pip-audit: `pip install pip-audit && pip-audit -r requirements.txt` — zero HIGH/CRITICAL
- [ ] Confirm no JWT in cookies: browser DevTools → Network → login response → no Set-Cookie header with JWT

### Key Rotation
- **JWT_SECRET_KEY rotation**: Invalidates ALL active sessions. Coordinate with users. Restart backend after rotation.
- **SMTP credentials**: Update `.env` and restart backend. No session impact.
- **TLS certificate renewal**: Certbot handles automatically if configured. Manual: replace cert.pem/key.pem and `nginx -s reload`.

## SOC2 Evidence Notes
- Security controls evidence: `docs/security/SECURITY_CONTROLS.md`
- Incident response runbook: `docs/security/INCIDENT_RESPONSE.md`
- Data inventory: `docs/security/DATA_CLASSIFICATION.md`
