## 1. Product Overview

ArthaBuild is a **customer-hosted SaaS platform** that automates the entire NetSuite development and implementation lifecycle. Customers deploy ArthaBuild entirely inside their own AWS VPC. No code, credentials, or data ever leaves the customer's infrastructure.

### 1.1 Core Value Proposition
- Automate SuiteScript generation, testing, and deployment via AI chat
- 100% air-gapped — runs inside the customer's AWS account
- Connects to NetSuite via standard TBA (Token-Based Authentication)
- Replaces weeks of manual ERP implementation work with minutes of AI-driven automation

### 1.2 Deployment Model
```
Customer's AWS VPC
┌──────────────────────────────────────────────────────────┐
│  [React Frontend]  →  [FastAPI Backend]                  │
│                            ↓                             │
│                   [Ollama LLM + FAISS]                   │
│                            ↓                             │
│                   [SuiteCloud CLI]                       │
│                            ↓                             │
│                   [Customer's NetSuite]                  │
└──────────────────────────────────────────────────────────┘
           ↕ License ping only (no data)
    ArthaBuild License Server (TechCloudPro AWS)
```

## 3. Module 1 — Platform Authentication

### 3.1 Overview
Users authenticate into the ArthaBuild platform using email/password. Auth runs entirely inside the customer's deployment. JWT tokens are used for session management.

### 3.2 Functional Requirements

#### FR-AUTH-01: User Registration
- User provides: full name, email, organization name, password
- Password must be: min 8 chars, 1 uppercase, 1 lowercase, 1 number, 1 special character
- Email must be unique per deployment
- On success: sends verification email, redirects to `/signup-success`
- On duplicate email: returns error "Email already registered"

**Test Cases:**

| TC-AUTH-04 | Missing email field | 422 Unprocessable Entity |
| TC-AUTH-05 | Invalid email format (no @) | 422 Unprocessable Entity |

#### FR-AUTH-02: Email Check (Pre-login)
- Frontend checks if email exists before showing password field

## 4. Module 2 — NetSuite Connection (Per-Session TBA)

### 4.1 Overview
Each time a user starts a session, they enter their NetSuite TBA credentials. These are stored **only in server-side memory for the duration of the session** — never written to disk, database, or logs. When the session ends, credentials are destroyed.

### 4.2 TBA Credentials Required
```
Account ID          (e.g., 7220160_SB2)
Consumer Key        (from NetSuite OAuth setup)
Consumer Secret
Token ID
Token Secret
```

### 4.3 Functional Requirements

#### FR-NS-01: Connect NetSuite
- User submits TBA credentials via modal in the chat header
- Backend validates by running a test SuiteCloud CLI command (`suitecloud account:setup`)
- On success: session flagged as `netsuite_connected = true`, credentials held in memory
- On failure: specific error returned (wrong account ID, invalid token, etc.)

**Test Cases:**
| ID | Input | Expected |
|----|-------|---------|
| TC-NS-01 | Valid TBA credentials | 200, `{ authenticated: true, account_name: "7220160_SB2", message: "..." }` |
| TC-NS-02 | Wrong Consumer Key | 401, generic auth failure message |
| TC-NS-03 | Wrong Account ID | 401, generic auth failure message |
| TC-NS-04 | Empty fields | 422 |
| TC-NS-05 | Sandbox account ID | 200, `{ authenticated: true, account_name: "..._SB2" }` (no `env` field) |
| TC-NS-06 | Production account ID | 200, `{ authenticated: true, account_name: "..." }` (no `env` field) |

#### FR-NS-02: Session Credential Isolation
- Each user session has its own isolated credential store
- User A's credentials CANNOT be used for User B's requests
- Credentials are cleared on logout, session expiry, or manual disconnect

**Test Cases:**
| ID | Scenario | Expected |
|----|----------|---------|
| TC-NS-07 | Two users connected simultaneously | Each gets their own NetSuite account context |
| TC-NS-08 | User logs out | Credentials wiped from memory immediately |
| TC-NS-09 | Session expires (24hr JWT) | Credentials wiped, user must reconnect |
| TC-NS-10 | API call without NetSuite connected | 401, "NetSuite session not found. Please authenticate first." |

#### FR-NS-03: Disconnect NetSuite
- User can manually disconnect
- Header shows connection status (green dot = connected, red = disconnected)

## 5. Module 3 — AI Chat (Core Product)

### 5.1 Overview
The chat interface connects to the FastAPI backend which routes to the local Ollama LLM via LangGraph RAG pipeline. The FAISS vectorstore (203K NetSuite knowledge chunks) powers Q&A. No queries leave the customer's VPC.

### 5.2 Intent Classification

The system classifies every user message into one of four intents before routing:

| Intent | Description |
|--------|-------------|
| `general_chat` | NetSuite Q&A, how-to, explanations (uses RAG) |
| `generate_suitescript` | AI generates SuiteScript JS + XML deployment file |
| `fetch_netsuite_data` | Pulls live data from NetSuite via SuiteCloud CLI |
| `manage_sdf_project` | Creates or deploys SDF projects |

### 5.3 Functional Requirements

#### FR-CHAT-01: Send Message
- User types message, hits Enter or clicks Send
- Loading spinner shown while processing
- Response streamed back token by token (not waiting for full response)
- Auto-scroll to latest message

**Test Cases:**
| ID | Input | Expected |
|----|-------|---------|
| TC-CHAT-01 | "What is SuiteScript 2.0?" | RAG answer from FAISS vectorstore |
| TC-CHAT-02 | Empty message | Send button disabled |
| TC-CHAT-03 | Message while loading | Input disabled, no double-send |
| TC-CHAT-04 | Very long message (5000 chars) | Accepted, processed normally |

#### FR-CHAT-02: Chat History
- All conversations persist in browser localStorage
- Sidebar shows list of chats sorted by most recent
- Chat auto-titled from first user message
- User can delete, rename chats

**Test Cases:**
| ID | Scenario | Expected |
|----|----------|---------|
| TC-CHAT-05 | New chat created | Appears in sidebar, title = first message summary |
| TC-CHAT-06 | Page refresh | All chats still present |
| TC-CHAT-07 | Delete chat | Removed from sidebar + localStorage |
| TC-CHAT-08 | Rename chat | Updated immediately in sidebar |

#### FR-CHAT-03: RAG Pipeline (general_chat)
- Query embedded with local embeddings
- FAISS similarity search returns top-k relevant chunks
- Grader checks relevance — if poor, rewrites query and retries
- Answer generated using Ollama LLM with context

**Test Cases:**
| ID | Query | Expected |

#### FR-CHAT-04: Session Memory
- Each chat session maintains conversation history
- LLM receives last N messages as context (configurable, default: 10)

**Test Cases:**

## 6. Module 4 — SuiteScript Generation & Deployment

### 6.1 Overview
When intent = `generate_suitescript`, the AI generates a complete SuiteScript file (JS) and its XML deployment manifest. The user reviews it, types "yes" to confirm, and the system saves and deploys via SuiteCloud CLI to their NetSuite account.

### 6.2 Functional Requirements

#### FR-SS-01: SuiteScript Generation
- User describes what they need (e.g., "Create a User Event script that makes Memo field mandatory on Sales Orders")
- AI generates:
  - Complete SuiteScript 2.1 JS file (with proper `define`, `N/record` imports, best practices)
  - XML deployment file in SDF format
  - Inline comments explaining each section
- Code displayed with syntax highlighting in chat
- "Yes to deploy" prompt shown after generation

**Test Cases:**
| ID | Input | Expected |
|----|-------|---------|
| TC-SS-01 | "Make memo mandatory on Sales Orders" | Valid SS 2.1 User Event script + XML |
| TC-SS-02 | "Create a scheduled script to send weekly reports" | Valid Scheduled Script + XML |
| TC-SS-03 | Vague input: "make a script" | Clarifying question asked |
| TC-SS-04 | Generated code contains `N/record` import | Correct module import verified in output |
| TC-SS-05 | User types "yes" after review | Files saved, deployment triggered |
| TC-SS-06 | User types "no" / requests changes | Re-generation with modifications |

#### FR-SS-02: File Saving
- On user confirmation ("yes"):
  - JS file saved to `TestSDFProject/src/FileCabinet/SuiteScripts/` with NetSuite naming convention
  - XML deployment file saved to `TestSDFProject/src/Objects/`
- Files saved with correct NetSuite standard names (e.g., `UserEventScript_MemoMandatory.js`)

**Test Cases:**

#### FR-SS-03: SDF Deployment to NetSuite
- Requires active NetSuite session (FR-NS-01)
- Runs `suitecloud project:deploy` inside `TestSDFProject/`
- Uses session TBA credentials (NOT global config)

## 7. Module 5 — Local LLM (Ollama)

### 7.1 Overview
All AI inference runs on the customer's own AWS instance using Ollama. No queries go to OpenAI or any external API. The FAISS vectorstore is shipped pre-built and re-embedded with local embeddings as part of the product package.

### 7.2 Model Stack

| Function | Model | Notes |
|----------|-------|-------|
| Chat generation | `llama3.1:8b` or `mistral:7b` | Via Ollama HTTP API |
| Embeddings | `nomic-embed-text` | Via Ollama, replaces OpenAI ada-002 |
| Intent classification | `llama3.1:8b` | Runs locally, replaces GPT-4 classifier |

### 7.3 Functional Requirements

#### FR-LLM-01: Ollama Integration ✅ DONE (03-01, 2026-04-09)
- FastAPI backend calls `http://localhost:11434` (Ollama default)
- Configurable via `OLLAMA_BASE_URL` env var
- Health check on startup: if Ollama not running, startup fails with clear message

**Test Cases:**
| ID | Scenario | Expected |
|----|----------|---------|
| TC-LLM-01 | Ollama running + model loaded | Chat works end-to-end |
| TC-LLM-02 | Ollama not running | Startup error: "Ollama not found at localhost:11434" |
| TC-LLM-03 | Model not pulled | Error: "Model llama3.1:8b not found, run: ollama pull llama3.1:8b" |
| TC-LLM-04 | Ollama crashes mid-session | "AI service unavailable" error in chat |

#### FR-LLM-02: Local Embeddings ✅ DONE (03-01, 2026-04-09)
- `nomic-embed-text` via Ollama used for:
  - Query embedding (real-time, per user message)
  - FAISS vectorstore must be rebuilt with `nomic-embed-text` (768-dim) to match
- Embedding dimension: 768 (vs OpenAI's 1536)

**Test Cases:**
| ID | Scenario | Expected |
|----|----------|---------|
| TC-LLM-05 | Query embedded and searched | Relevant FAISS chunks returned |
| TC-LLM-06 | Embedding model not loaded | Clear error message |
| TC-LLM-07 | FAISS dimension mismatch | Startup validation catches this |

#### FR-LLM-03: OpenAI Key Removal ✅ DONE (03-01, 2026-04-09)
- Zero OpenAI API keys in codebase
- All `openai_api_key=` references replaced with Ollama equivalents
- Environment variables documented, no hardcoded keys

**Test Cases:**

## 9. Module 7 — License Server

### 9.1 Overview
ArthaBuild's central server (hosted on TechCloudPro AWS) handles license validation only. It receives: license key, account ID, version. It sends back: valid/invalid, expiry date. **No customer data, no prompts, no NetSuite info ever reaches this server.**

### 9.2 Functional Requirements

#### FR-LICENSE-01: License Validation
- On startup, backend sends `POST /api/license/validate` with license key
- Response: `{ valid: true, expiry: "2027-01-01", tier: "professional" }`
- If invalid/expired: backend starts in read-only demo mode (no NetSuite connection, no deployment)
- Checks: on startup + every 24 hours

**Test Cases:**
| ID | Scenario | Expected |
|----|----------|---------|
| TC-LIC-01 | Valid license key | Full features enabled |
| TC-LIC-02 | Expired license | Demo mode, banner shown to user |
| TC-LIC-03 | License server unreachable | Cached validation used (grace period: 72hr) |
| TC-LIC-04 | Tampered license key | 403, demo mode |

## 10. Non-Functional Requirements

### 10.1 Security
| Requirement | Detail |
|-------------|--------|
| NFR-SEC-01 | TBA credentials NEVER written to disk, DB, or logs |
| NFR-SEC-02 | JWT signed with HS256, min 32-char secret |
| NFR-SEC-03 | All passwords hashed with bcrypt (cost factor ≥ 12) |
| NFR-SEC-04 | No OpenAI or external API keys in codebase |
| NFR-SEC-05 | HTTPS enforced in production (TLS via nginx) |
| NFR-SEC-06 | Rate limiting: 10 req/min on auth endpoints |
| NFR-SEC-07 | SQL injection prevention via SQLAlchemy ORM only |
| NFR-SEC-08 | CORS restricted to same-origin in production |

| NFR-PERF-02 | RAG answer (general_chat) < 15 seconds on 8B model |
| NFR-PERF-03 | SuiteScript generation < 30 seconds |
| NFR-PERF-04 | FAISS similarity search < 500ms |
| NFR-PERF-05 | Frontend initial load < 3 seconds |

### 10.3 Data Isolation
