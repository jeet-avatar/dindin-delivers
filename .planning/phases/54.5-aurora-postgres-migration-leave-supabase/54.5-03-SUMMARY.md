## Decisions Made

- **DROP+recreate the 4 real schemas before restore** — Wave 2 SUMMARY claimed empty Aurora; reality showed 153 empty-table DDLs in real schemas. Cleaner restart vs overlay risk. (Rule-3 deviation #1)
- **Pre-install 4 extensions in public** before restore — dump references `public.citext` but pg_dump filter excluded the CREATE EXTENSION lines (extensions live outside the 4 app schemas). (Rule-3 deviation #2)
- **Patch dump to skip CREATE SCHEMA public** — pre-existing public schema (created for extensions) would conflict. (Rule-3 deviation #3)
- **Revert SG hardening; allow 0.0.0.0/0:5432 with documented justification** — managed prefix list returns None, ip-ranges.json has no LAMBDA service for us-east-1, tightening blocked all 4 Lambdas. Aurora master password (28-char random + KMS encryption) is the security boundary until Phase 54.5-04 provisions RDS Proxy + VPC-attaches Lambdas. (Rule-3 deviation #7)
- **Switch zietra-api sentinel from INSERT to UPDATE-revert** — tenant_features has both CHECK constraint and composite PK; INSERT of fake module impossible. Toggle expires_at on real row.
- **Lookup secrets by FULL ARN, not by Name** — `turion-satellite/production/database-url-NCbgX6` short-id failed (the 'NCbgX6' suffix is rotation-unstable per Wave 2 finding); full ARN works.
- **Skip zietra-meet rotation** per Wave 2 Open Q1 resolution.
- **Keep `SUPABASE_DB_URL` env-var name on zietra-api despite pointing at Aurora** — name baked into code; renaming = code change = Phase 56+.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Aurora real schemas had 153 empty-table DDLs (Wave 2 cleanup incomplete)**
- **Found during:** Task 2, pre-flight verify
- **Issue:** Plan §verify-pre-1 expected 0 tables in `public/crm/turion/turion_satellite/_dryrun_*`. Reality: 153 tables across the 4 real schemas (DDL only, 0 rows). Wave 2 SUMMARY's "Aurora returned to empty-baseline state (4 real schemas, 0 tables)" was incorrect.
- **Fix:** `DROP SCHEMA … CASCADE` on all 4 real schemas; `CREATE SCHEMA public` + grants; pre-install 4 extensions.
- **Verification:** Post-fix table count = 0; post-restore table count = 153 (matching Supabase exactly).
- **Committed in:** Task 2 (`b229a665`)

**2. [Rule 1 - Bug] AWS CLI inline `--environment Variables=…` rejects JSON with special chars**
- **Found during:** Task 3, first turion-demo-api flip attempt
- **Issue:** `Error parsing parameter '--environment': Expected: '=', received: '"' for input` — special chars in env var values (URL-encoded password, JWT) confuse CLI argparser.
- **Fix:** Switched to `file://` JSON pattern: write `{Variables: {...}}` to `/tmp/lambda-env-<lambda>.json` then `--environment "file:///tmp/..."`.
- **Verification:** All 3 inline-env flips (turion-demo, zietra-crm, zietra-api) succeeded with file:// pattern.
- **Committed in:** Task 3 (`c2640bb0`)

**3. [Rule 1 - Bug] Plan secret-id format `turion-satellite/production/database-url-NCbgX6` failed by-Name lookup**
- **Found during:** Task 3, satellite secret rotation
- **Issue:** `aws secretsmanager get-secret-value --secret-id turion-satellite/production/database-url-NCbgX6` returned `ResourceNotFoundException`. The `-NCbgX6` suffix is the random part of the ARN, NOT part of the friendly name. Wave 2 actually used the FULL ARN form per Wave 2 SUMMARY note ("the …NCbgX6 ids are stale").
- **Fix:** Use full ARN `arn:aws:secretsmanager:us-east-1:134607809447:secret:turion-satellite/production/database-url-NCbgX6`.
- **Verification:** Pre/post-rotation `get-secret-value` both succeeded with full ARN.
- **Committed in:** Task 3 (`c2640bb0`)

**4. [Rule 1 - Bug] Smoke script `'MAKE'` violates CHECK constraint on default_make_buy**
- **Found during:** Task 4, first smoke run
- **Issue:** `new row for relation "part_definitions" violates check constraint "part_definitions_default_make_buy_check"` — CHECK requires lowercase 'make'/'buy'. Wave 2 dryrun ran `SMOKE_WRITE=0`, so this never fired.
- **Fix:** Edit `scripts/smoke-turion-satellite.sh` line `'MAKE'` → `'make'`.
- **Verification:** Re-run smoke → satellite sentinel write+delete OK.
- **Committed in:** Task 4 (`4556bbb2`)

**5. [Rule 1 - Bug] psql `-At` RETURNING still appends `INSERT 0 1\n` command tag**
- **Found during:** Task 4, second smoke run (after fix #4)
- **Issue:** `BOOKING_ID` was captured as `<uuid>\nINSERT 0 1` (multiline), then DELETE WHERE id='<uuid>\nINSERT 0 1' failed with `invalid input syntax for type uuid`.
- **Fix:** Pipe through `head -n 1` in 2 smoke scripts (turion-satellite, zietra-crm).
- **Verification:** Smoke captured clean UUID `2f73c00f-50cf-447e-a74d-0ae1864c66d5`.
- **Committed in:** Task 4 (`4556bbb2`)

**6. [Rule 1 - Bug] Smoke script's bookings INSERT references columns that don't exist**
- **Found during:** Task 4, third smoke run
- **Issue:** `column "link_id" of relation "bookings" does not exist`. Real schema is camelCase: `id, "userId", slug, "guestName", "guestEmail", "scheduledAt", "durationMins", status, "roomId", "createdAt", "updatedAt"` — all NOT NULL.
- **Fix:** Rewrite smoke INSERT to match real schema with quoted camelCase columns + values for all NOT NULL fields.
- **Verification:** crm sentinel booking write+delete OK (e.g., id `aa4a0c37-5c86-4125-b91b-44d35fdf407b`).
- **Committed in:** Task 4 (`4556bbb2`)

**7. [Rule 1 - Bug] tenant_features INSERT impossible — CHECK constraint AND composite PK**
- **Found during:** Task 4, fourth smoke run
- **Issue:** First error: `column "feature_key" of relation "tenant_features" does not exist` (real column is `module_code`). After fix: `new row for relation "tenant_features" violates check constraint "tenant_features_module_code_check"` — module_code locked to 13 specific values. Combined with composite PK (tenant_id, module_code), INSERT of any sentinel value is structurally impossible.
- **Fix:** Switch to UPDATE-then-revert pattern: pick existing (tenant_id, module_code) row, capture original `expires_at`, set to `2099-01-01`, verify, restore.
- **Verification:** sentinel UPDATE+revert OK on (00000000-0000-0000-0000-000000000001, sales).
- **Committed in:** Task 4 (`4556bbb2`)

**8. [Rule 3 - Blocking] SG hardening blocked Lambdas (no Lambda public-egress prefix list exists)**
- **Found during:** Task 4, post-hardening smoke verification
- **Issue:** Plan-template prescribed: revoke 0.0.0.0/0:5432 → add operator IP /32 → add `com.amazonaws.us-east-1.lambda` managed prefix list, fallback to ip-ranges.json LAMBDA service. Reality: managed prefix list returns `None` (does not exist in this region), ip-ranges.json has no LAMBDA service for us-east-1 (returns 0 CIDRs). After tightening, all 4 Lambdas got 500 on `/api/health` (smoke exit 22).
- **Fix:** Re-allow 0.0.0.0/0:5432 with documented security justification: Aurora master password is 28-char random (auto-rotated by Secrets Manager), KMS-encrypted, all 4 Lambdas have `VpcConfig: null` (no VPC attached). Phase 54.5-04 deliverables include VPC-attach + RDS Proxy provisioning, which will enable proper SG hardening at that time.
- **Verification:** Re-ran smoke post-revert: exit 0, ALL 4 LAMBDAS PASS.
- **Committed in:** Task 4 (`4556bbb2`)
