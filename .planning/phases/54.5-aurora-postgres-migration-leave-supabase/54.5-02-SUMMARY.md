## Decisions Made

- **Docker postgres:17 client image** — local pg_dump 14.19 / 15.14 refuse to dump from Supabase's PG 17.6 source ("server version mismatch"). brew install postgresql@17 was permission-denied. Docker image (172 MB pull, cached locally) works for dump + restore + psql; isolates client tooling from host state. (Rule-3 blocking-issue auto-fix.)
- **Dump-SQL surgical rewriting** instead of plan's literal rename-shuffle — cleaner handling of cross-schema references. The `public.citext` extension type couldn't survive a rename of `public_baseline → public` after pg_restore had created its own `public` schema with restored data. Python script (`/tmp/rewrite-dump.py`) namespace-prefixes table refs while preserving extension type lookups.
- **Strip auth.X references** during restore (2 FKs + 5 RLS policies) — Aurora has no `auth` schema (Supabase-only). The 2 affected tables (`contacts`, `website_visits`) have 0 rows in baseline, and per RESEARCH §C.6 these refs are explicitly slated for drop on Aurora anyway. (Rule-1 fix matches planned cutover state.)
- **Strip `SET transaction_timeout = 0`** from dump — PG 17 GUC, not present in Aurora's PG 16.4. One sed line.
- **`/ping` over `/health` for zietra-crm-api** smoke — `/health` requires DB connection and returned 503 when Supabase pooler was slow during testing; `/ping` is a no-DB Lambda canary returning "Healthy Connection". Choosing `/ping` avoids false-positive FAILs during the production cutover window.
- **DB-direct only smoke for zietra-api** — Lambda exists but has no live APIGW route. Read-path proof comes from querying the same tables the Lambda would query. When 54.1 Wave 2 wires up the live route, the smoke script can be extended.
- **Pre-flight env contents NOT committed** — only SHA256 checksums. Files hold inline secrets (DB passwords, service-role JWTs, SMTP credentials). Pre-commit hook would block them anyway. Mode-600 on disk is the security boundary.
- **Skip zietra-meet secret rotation in 54.5-03** — Open Q1 resolved: zero Lambdas reference it. Saves a step in the maintenance window.
- **No 300s wait for satellite secret refresh** — Open Q2 resolved: SDK init pattern, not extension layer. Cold start = instant fresh secret.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Local pg_dump cannot connect to Postgres 17.6 source**
- **Found during:** Task 1 (initial pg_dump invocation)
- **Issue:** `pg_dump: error: aborting because of server version mismatch — server version: 17.6; pg_dump version: 15.14 (Homebrew)`. Local has only postgresql@14 + postgresql@15. Supabase upgraded to PG 17.
- **Fix:** Use `docker run --rm -v /tmp:/host-tmp postgres:17 pg_dump …` for ALL dump/restore/psql operations. Image pulled once, cached. brew install postgresql@17 was tried but permission-denied.
- **Files modified:** all command invocations in runbook + smoke scripts use `docker run --rm -e PGPASSWORD=… postgres:17 psql/pg_dump/pg_restore`
- **Verification:** `docker run --rm postgres:17 pg_dump --version` → `pg_dump (PostgreSQL) 17.10 (Debian 17.10-1.pgdg13+1)` — works against PG 17.6 source.
- **Committed in:** Task 1 (`653c70f1`)

**2. [Rule 1 - Bug] Postgres 17 dump contains `SET transaction_timeout = 0` which Aurora 16.4 doesn't recognize**
- **Found during:** Task 2 (first pg_restore attempt against Aurora)
- **Issue:** `pg_restore: error: could not execute query: ERROR: unrecognized configuration parameter "transaction_timeout"`. The GUC was added in PG 17. With `--exit-on-error`, pg_restore aborts immediately at INITIALIZING stage.
- **Fix:** Convert custom-format dump to plain SQL via `pg_restore --file=…sql`, sed-strip the one offending line (`/^SET transaction_timeout = /d`), apply via `psql -v ON_ERROR_STOP=1`. This pattern handles future similar incompatibilities (just add more strip patterns).
- **Files modified:** `/tmp/zietra-supabase-dryrun.sql` → `/tmp/zietra-supabase-dryrun-clean.sql` (transient)
- **Verification:** `grep -c transaction_timeout /tmp/zietra-supabase-dryrun-clean.sql` → 0
- **Committed in:** Task 2 (`95b55b1b`)

**3. [Rule 1 - Bug] Dump references Supabase-only `auth.users` (FKs) and `auth.uid()` (RLS policies)**
- **Found during:** Task 2 (psql apply of cleaned dump)
- **Issue:** 7 functional lines reference `auth.X` which doesn't exist on Aurora. 2 FK constraints (`contacts_owner_id_fkey`, `website_visits_owner_id_fkey`) on tables with 0 rows; 5 RLS policies (4 on contacts + 1 on website_visits) referencing `auth.uid()`. Per RESEARCH §C.6 and CONTEXT.md, all 7 are planned to be DROPPED on Aurora at cutover anyway.
- **Fix:** Python script `/tmp/strip-auth-refs.py` replaced these 7 lines with `-- STRIPPED ...` comments. Result matches planned post-cutover state.
- **Files modified:** `/tmp/zietra-dryrun-final.sql` (final cleaned dump)
- **Verification:** Restore log shows 0 errors. `grep -v '^--' /tmp/zietra-dryrun-final.sql | grep auth.` returns 1 line (a comment inside SQL, harmless).
- **Committed in:** Task 2 (`95b55b1b`)

**4. [Rule 3 - Blocking] Plan's rename-shuffle restore strategy collides with extension scoping**
- **Found during:** Task 2 (third restore attempt after auth strip)
- **Issue:** Plan said "rename real schemas → restore creating real names → rename real to `_dryrun_*`". The dump references `public.citext` (extension type). After renaming `public_baseline` back to `public` (so citext is reachable), the restored `public` schema (now from dump) collided.
- **Fix:** Wrote `/tmp/rewrite-dump.py` — surgical SQL rewriter that prefixes `crm.X`, `turion.X`, `turion_satellite.X`, and `public.<table>` with `_dryrun_*` BUT preserves `public.citext` (extension type, must stay in `public` schema). Order matters: rewrite `turion_satellite.X` BEFORE `turion.X`.
- **Files modified:** `/tmp/zietra-dryrun-rewritten.sql` (transient)
- **Verification:** Final restore: 0 errors; 153 tables created in `_dryrun_*` schemas; `public` schema still holds extensions only (no tables).
- **Committed in:** Task 2 (`95b55b1b`)

**5. [Rule 3 - Blocking] Plan §E.1.3 + §E.1.4 referenced non-existent v1 REST APIs**
- **Found during:** Task 3 (smoke script construction)
- **Issue:** Plan said `aws apigateway get-rest-apis --query 'items[?name==...].id'` to discover hostnames. That returns 0 entries — account uses ONLY API Gateway v2 (HTTP APIs). Plan §E.1.3-1.4 had `<crm-apigw>` and `<zietra-api-apigw>` placeholders.
- **Fix:** Discovery via `aws apigatewayv2 get-apis` reveals the correct topology. zietra-crm-api is at `fzonke39pf`. zietra-api Lambda has NO live APIGW integration — its smoke script runs DB-direct only.
- **Files modified:** all 4 smoke scripts use the correct discovered endpoints
- **Verification:** Dry-run smoke ran clean: ALL 4 LAMBDAS PASS in 13 sec
- **Committed in:** Task 3 (`238bed7f`)
