## Summary

This is a small, low-risk migration: **25 MB Postgres database, 4 Lambdas, 4 app schemas, 0 paid users, 0 Supabase-specific feature usage in app code.** The audit (CONTEXT.md) established that the only Supabase-specific artifacts are (a) the `supabase_vault` extension on an empty schema and (b) 5 RLS policies on 2 empty tables — both safe to drop.

**Primary recommendation:** Option A networking — **public Aurora endpoint with security-group allowlist**, no VPC attachment for Lambdas. Skip RDS Proxy. Use Aurora Serverless v2 Postgres 16.4 with ACU range 0.5–4 (Aurora Standard, NOT I/O-Optimized) → estimated **$45–60/month**.

**Why public+SG over Lambdas-in-VPC:**
1. Modern Hyperplane ENI architecture (2019+) reduces VPC cold-start penalty to 50–100 ms — but it still adds setup time on the FIRST cold start per (subnet, SG) combo, requires NAT gateway (~$32/mo per AZ × 2 = $64/mo) for Lambdas to reach Cognito/SES, and complicates the existing build-and-push.sh deploy flow.
2. The 4 Lambdas already use TLS to reach the public Supabase pooler — there is no "we need to be in a VPC" baseline to honour. Aurora's own TLS + IAM authentication + tight SG allowlist provides equivalent security with zero VPC ops burden.
3. RDS Proxy on Serverless v2 has an **8-ACU minimum bill = ~$144/mo** ([Strobes](https://strobes.co/blog/how-we-managed-aurora-serverless-v2-idle-connections-in-rds-proxy-and-saved-rds-costs-by-50/)) — disqualifying for a $50/mo target. App-side connection pooling (one `pg.Pool` per Lambda container, sized 1–3) is sufficient for 4 demo Lambdas.

**Cutover sequence is ~6 minutes wall-clock** for 25 MB at typical home-broadband upload speed. Risk is dominated by operator error (wrong endpoint in secret, missed Lambda) — not by tooling. Mitigation: dry-run against a staging Aurora cluster (or staging schema on the production cluster) before the real window.

## A. Aurora Serverless v2 Cluster Provisioning

### A.1 Engine version + cluster identity

**Engine:** `aurora-postgresql`
**Engine version:** `16.4` — latest GA Postgres 16 supported by Aurora as of May 2026 ([Aurora Postgres extension versions](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraPostgreSQLReleaseNotes/AuroraPostgreSQL.Extensions.html)). Pin major version to 16; allow minor auto-upgrades during maintenance window.
**Cluster identifier:** `zietra-aurora-prod` (matches existing `dollor-*` and `zietra-*` naming).
**Database name (initial):** `zietra` (single logical database, all 4 schemas live inside).
**Master username:** `zietra_admin` (avoid `postgres` to reduce default-creds attack surface).
**Master password:** Auto-generated via `--manage-master-user-password` → AWS auto-creates a Secrets Manager secret named `rds!cluster-<uuid>` and rotates it on demand.

### A.2 Networking pre-requisites (one-time per region)

Use the **default VPC** in `us-east-1` (account `134607809447`). Aurora requires a DB subnet group spanning ≥2 AZs ([AWS DB subnet group requirements](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html)).

```bash
# Discover default VPC + its subnets
DEFAULT_VPC=$(aws ec2 describe-vpcs --filters Name=is-default,Values=true \
  --query 'Vpcs[0].VpcId' --output text --region us-east-1)

SUBNETS=$(aws ec2 describe-subnets --filters Name=vpc-id,Values=$DEFAULT_VPC \
  --query 'Subnets[*].SubnetId' --output text --region us-east-1)
# Pick subnets in ≥2 distinct AZs (default VPC has one per AZ — usually 6 in us-east-1)

# Create DB subnet group covering ≥2 AZs
aws rds create-db-subnet-group \
  --db-subnet-group-name zietra-aurora-subnets \
  --db-subnet-group-description "Zietra Aurora Serverless v2 — public endpoint, default VPC" \
  --subnet-ids $SUBNETS \
  --region us-east-1
```

### A.3 Security group (Aurora ingress)

**Decision:** Public endpoint + SG allowlist. Allow ingress on TCP/5432 from:

- Tighten post-cutover to: AWS Lambda service IP ranges in `us-east-1` (published via `ip-ranges.json`) + dev laptop public IPs.

**Better long-term:** Use IAM database authentication so even with public endpoint, only IAM-authed callers can connect. Defer to Phase 56 (M3).

# Post-cutover hardening (manual, after smoke passes):
# Replace 0.0.0.0/0 with: home/office /32 + Lambda subnets if Option B chosen

### A.4 KMS encryption

Use **default AWS-managed KMS key for RDS** (`alias/aws/rds`). No custom key needed for demo workload. Aurora storage is always encrypted; this just picks the key.

### A.5 Parameter group

Aurora ships defaults for `shared_preload_libraries` that already include `pg_stat_statements`. The 5 extensions Supabase had in use (`citext`, `pg_stat_statements`, `pgcrypto`, `plpgsql`, `uuid-ossp`) are **all available** on Aurora Postgres 16 ([Extension versions for Aurora PostgreSQL](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraPostgreSQLReleaseNotes/AuroraPostgreSQL.Extensions.html)). `supabase_vault` is **not** available — drop per CONTEXT.md decision.

For demo workload, use the default cluster parameter group (`default.aurora-postgresql16`). If we later need custom logging or autovacuum tuning, create a custom group then. **Don't pre-optimise.**

### A.6 Cluster creation (the actual command)

```bash
aws rds create-db-cluster \
  --db-cluster-identifier zietra-aurora-prod \
  --engine aurora-postgresql \
  --engine-version 16.4 \
  --master-username zietra_admin \
  --manage-master-user-password \
  --database-name zietra \
  --db-subnet-group-name zietra-aurora-subnets \
  --vpc-security-group-ids $SG_ID \
  --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=4 \
  --backup-retention-period 7 \
  --preferred-backup-window "07:00-09:00" \
  --preferred-maintenance-window "sun:09:00-sun:11:00" \
  --storage-encrypted \
  --enable-cloudwatch-logs-exports '["postgresql"]' \
  --enable-iam-database-authentication \
  --tags Key=Project,Value=Zietra Key=Environment,Value=production Key=Phase,Value=54.5 \
  --region us-east-1
```

**ACU rationale (0.5 min / 4 max):**
- Min 0.5 ACU = 1 GiB RAM, ~$43/mo if always-on. Defer scale-to-zero (min=0) to Phase 56+ — autopause adds 10–30s wake-up latency on first request after pause, painful for live demo.
- Max 4 ACU = 8 GiB RAM, ~$345/mo at sustained ceiling. With our 25 MB DB + 4 demo Lambdas, sustained spend will hover at min (0.5) — average bill ~$45–60/mo.
- ACU valid values: 0, 0.5, 1, 1.5, 2, ... in steps of 0.5 up to 256 ([AWS docs](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.html)).

**Why NOT scale-to-zero (min=0):** Available since Nov 2024 ([AWS announcement](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-aurora-serverless-v2-scaling-zero-capacity/)) for Postgres 16.3+. But autopause delay 5min–24h, and resume from pause adds latency to first request. Unsuitable for live demo URLs. Re-evaluate in Phase 56 once tenant onboarding patterns are clearer.

**Why NOT I/O-Optimized:** Costs $0.156/ACU-hr vs $0.12 for Standard, and $0.225/GB storage vs $0.10 ([CloudFix](https://cloudfix.com/blog/aurora-io-optimized-vs-standard/)). Worth it only if I/O exceeds 25% of bill — at 25 MB demo workload, I/O is rounding error. Stick with Standard.

## B. Networking Decision (CRITICAL)

### B.1 The two options summarized

| Aspect | Option A: Public Aurora + SG | Option B: Private Aurora + Lambdas-in-VPC |
|--------|------------------------------|-------------------------------------------|
| Aurora endpoint | Public (DNS resolves to public IP, but only allowlisted SGs reach it) | Private (in private subnet, no public IP) |
| Lambda config change | None (env var swap only) | `--vpc-config SubnetIds=...,SecurityGroupIds=...` on all 4 Lambdas |
| Lambda → Cognito/SES/Anthropic egress | Direct (current state — internet via Lambda's hidden VPC) | Requires NAT gateway in same VPC subnets (~$32/mo per AZ × 2 = ~$64/mo) |
| Cold-start penalty | None (current ~200 ms baseline) | +50–100 ms per cold start ([AWS blog 2019 + 2025 confirms](https://aws.amazon.com/blogs/compute/announcing-improved-vpc-networking-for-aws-lambda-functions/)). First-ever cold start per (subnet, SG) combo can be 1–2s longer (Hyperplane ENI provisioning) |
| Operational complexity | Low (one SG, one allowlist) | High (VPC subnets, NAT, route tables, NACLs, VPC endpoints to avoid NAT for AWS service calls) |
| Security posture | TLS + SG allowlist + IAM auth (when enabled). Public endpoint surface but locked down. | Zero public surface |
| Build-and-push.sh impact | Zero | Each Lambda's deploy script unchanged, but `update-function-configuration --vpc-config` becomes a manual step. Or we add `--vpc-config` to `update-function-code` — currently not in scripts. |
| Monthly cost delta | $0 | +$64/mo (NAT × 2 AZ for HA) |
| Time to provision | ~5 min | ~30 min (NAT + route tables + Lambda VPC attach × 4 + ENI warm-up × 4) |

### B.2 Recommendation: **Option A (public Aurora + SG)**

Reasoning:

1. **Threat model.** Aurora endpoint over TLS with strong password (auto-generated 32-char) + IAM database authentication enabled = effectively as private as a private endpoint. Adversary needs valid IAM credentials + password to even attempt connection. This matches what we already accept for Supabase (which is also a public pooler).
2. **Cost.** Option B adds ~$64/mo NAT cost — that's 100% surcharge on a $50/mo Aurora bill. Unjustifiable for a 4-Lambda demo workload.
3. **Cold start.** All 4 Lambdas serve interactive demo URLs. The 50–100 ms VPC penalty is 25–50% of current cold-start budget. Compounding across the call chain (e.g., zietra-api → zietra-crm-api), end-user latency suffers.
4. **Build/deploy flow.** CONTEXT.md establishes that `build-and-push.sh` for both turion Lambdas is the deploy idiom. Adding VPC config means adding a non-idempotent step to those scripts (or maintaining VPC config out-of-band) — operational drag for zero security gain over Option A.
5. **Reversibility.** If we ever need Option B (paid customers, compliance audit), adding VPC config is a future Phase 90+ change — non-blocking.

**Hardening for Option A (defer to post-cutover, NOT blocking):**
- Tighten SG to specific CIDRs after smoke (drop 0.0.0.0/0 → home + office /32 + Lambda subnets if needed for diagnostics).
- Enable IAM database authentication for app users (not master), then app-side connection string uses `auth-mode=iam` and Lambda role has `rds-db:connect` permission. Defer to M3 (Phase 56) so we don't blow this phase scope.

### B.3 RDS Proxy: **Skip**

CONTEXT.md open question 9 suggests RDS Proxy. **Recommend AGAINST** for this phase.

**Cost killer:** RDS Proxy on Serverless v2 has an **8-ACU minimum bill** at $0.025/ACU-hr → **8 × 0.025 × 730 = $146/month** ([Strobes](https://strobes.co/blog/how-we-managed-aurora-serverless-v2-idle-connections-in-rds-proxy-and-saved-rds-costs-by-50/), [Dev.to cost trap analysis](https://dev.to/aws-builders/caught-in-a-cost-optimization-trap-aurora-serverless-v2-with-rds-proxy-2mng)). That's 3× our Aurora cost itself.

**Real need:** Lambda connection storms. With 4 Lambdas, each at ~10 concurrent executions during a busy demo, max active connections ≈ 40. Aurora at 0.5 ACU supports ~189 connections (proportional to ACU memory; provisioned r6g.large allows 1000+). We're well under limit.

**App-side mitigation (free):** Each Lambda's `pg.Pool` config — `max: 2, idleTimeoutMillis: 1000` — keeps connections short-lived per warm container. The existing turion Lambdas already use `pg` Node driver; a one-line pool config tweak is sufficient.

**Re-evaluate RDS Proxy** when:
- We have ≥3 paid tenants generating sustained traffic
- Aurora connection count alarms fire (Section G)
- We move to a higher ACU floor (≥2) where the 8-ACU proxy minimum becomes <2× the DB bill

## C. Schema Dump + Restore Mechanics

### C.1 Pre-flight on Supabase (read-only verification)

Before dumping, capture the source-of-truth row counts:

```bash
# Connect to Supabase via DIRECT port 5432 (NOT pgbouncer 6543 — pg_dump needs session-mode)
SUPA_URL='postgres://postgres.lbpkbpfwdpnwlccmlfxn:<PW>@aws-1-us-east-2.pooler.supabase.com:5432/postgres'

# Save baseline row counts (used for parity check post-restore)
psql "$SUPA_URL" -At -c "
  SELECT schemaname || '.' || tablename || ',' ||
         (xpath('/row/c/text()', query_to_xml(
            format('SELECT COUNT(*) AS c FROM %I.%I', schemaname, tablename),
            false, true, '')))[1]::text::int
  FROM pg_tables
  WHERE schemaname IN ('public', 'crm', 'turion', 'turion_satellite')
  ORDER BY 1;
" > /tmp/supabase-baseline-counts.csv

wc -l /tmp/supabase-baseline-counts.csv  # expect 153
```

**On port choice:** CONTEXT.md says all 4 Lambdas connect via pgbouncer port `:6543`. `pg_dump` requires session-mode Postgres (transactions, replication slots not supported in pgbouncer transaction mode) → **must use port `:5432` direct**. This is a tooling-time concern, not a runtime concern. The Aurora connection string for the Lambdas will use the standard Aurora endpoint on port `:5432` (Aurora doesn't run pgbouncer; one connection per Lambda invocation, pooled at app level).

### C.2 The dump command

```bash
DUMP_FILE=/tmp/zietra-supabase-$(date +%Y%m%d-%H%M%S).dump

pg_dump "$SUPA_URL" \
  --format=custom \
  --no-owner \
  --no-privileges \
  --no-publications \
  --no-subscriptions \
  --schema=public \
  --schema=crm \
  --schema=turion \
  --schema=turion_satellite \
  --exclude-table='public._supabase_*' \
  --verbose \
  --file=$DUMP_FILE

ls -lh $DUMP_FILE  # expect ~5–15 MB compressed (custom format)
```

**Flag rationale:**
- `--format=custom` (`-Fc`): binary, compressed, parallel-restorable with `pg_restore --jobs=N`. Best for >100 MB DBs but cheap insurance even at 25 MB.
- `--no-owner`: strips `ALTER TABLE ... OWNER TO postgres.lbpkbpfwdpnwlccmlfxn` lines that would fail on Aurora (the Supabase service user doesn't exist there). Per [Supabase migration docs](https://supabase.com/docs/guides/platform/migrating-to-supabase/postgres) and [AWS RDS migration best practices](https://aws.amazon.com/blogs/database/best-practices-for-migrating-postgresql-databases-to-amazon-rds-and-amazon-aurora/).
- `--no-privileges`: strips GRANT statements referencing Supabase-only roles like `service_role`, `authenticated`, `anon`. Aurora doesn't have these.
- `--no-publications --no-subscriptions`: drops Supabase Realtime publication setup (we don't use Realtime per CONTEXT.md).
- `--schema=...`: explicit allowlist of 4 app schemas. Skips `auth`, `storage`, `realtime`, `graphql`, `graphql_public`, `extensions`, `pgbouncer`, `vault`. (Could use `-N vault -N auth ...` but `-n` allowlist is safer — adds nothing we don't want.)
- `--exclude-table='public._supabase_*'`: defensive — Supabase sometimes plants helper tables in `public`. Safe to skip.

### C.3 Restore to Aurora

Pre-restore: extensions are already created (Section A.11). Then:

```bash
# Connect string for Aurora master
AURORA_URL="postgres://zietra_admin:$(printf '%s' "$MASTER_PW" | jq -sRr @uri)@$WRITER:5432/zietra"

# Restore with parallel jobs
pg_restore \
  --dbname="$AURORA_URL" \
  --no-owner \
  --no-privileges \
  --jobs=4 \
  --verbose \
  --exit-on-error \
  $DUMP_FILE 2>&1 | tee /tmp/restore.log

# Expected: hundreds of CREATE TABLE / CREATE INDEX / COPY lines, zero ERROR lines
grep -i error /tmp/restore.log  # must be empty
```

**Why `--jobs=4` is safe at 25 MB:** Restore wall-time goes from ~10s sequential to ~3s parallel. No real-world benefit at this size, but harmless and future-proofs the runbook for when DB grows.

**Why `--exit-on-error`:** We want hard fail on first ERROR (e.g., missing extension, FK target row not yet restored) — not 30 minutes of soft-fail logs to triage. With `-Fc` and a well-formed dump, FK ordering is handled automatically.

### C.4 Sequence resync

Postgres sequences are restored at their dump-time value. In a quiescent dump (no writes during dump) this is correct, but it's belt-and-suspenders to re-sync each sequence to `MAX(id)+1` of its owning table:

```bash
psql "$AURORA_URL" -At -f - <<'SQL' > /tmp/sequence-resync.sql
SELECT 'SELECT setval(' ||
       quote_literal(quote_ident(n.nspname) || '.' || quote_ident(s.relname)) ||
       ', COALESCE(MAX(' || quote_ident(a.attname) || '), 1)) FROM ' ||
       quote_ident(tn.nspname) || '.' || quote_ident(t.relname) || ';'
FROM pg_class s
JOIN pg_namespace n ON n.oid = s.relnamespace
JOIN pg_depend d ON d.objid = s.oid AND d.deptype = 'a'
JOIN pg_class t ON t.oid = d.refobjid
JOIN pg_namespace tn ON tn.oid = t.relnamespace
JOIN pg_attribute a ON a.attrelid = t.oid AND a.attnum = d.refobjsubid
WHERE s.relkind = 'S'
  AND n.nspname IN ('public', 'crm', 'turion', 'turion_satellite');
SQL

# Execute the generated resync statements
psql "$AURORA_URL" -f /tmp/sequence-resync.sql
```

If output is empty (no sequences in those schemas — Prisma typically uses UUIDs), this is a no-op. Run it anyway.

## H. Risks + Mitigations

### H.1 Risk register (8 specific risks)

1. **Risk: pg_restore fails because `--no-owner` strips owner but app code expects specific role grants.**
   - **Likelihood:** LOW — CONTEXT.md verified zero `@supabase/*` imports and no RLS-using code paths.
   - **Mitigation:** Aurora master user `zietra_admin` owns everything post-restore. App connects as master initially. Per-app RLS roles deferred to M3 (Phase 56).
   - **Detection:** Restore log greps for `permission denied` or `must be owner of`.

2. **Risk: `supabase_vault` references in dump cause restore errors.**
   - **Likelihood:** LOW — vault schema is excluded by `--schema=` allowlist (Section C.2).
   - **Mitigation:** Allowlist guarantees no vault objects in dump. Verify with `pg_restore --list dump.file | grep -i vault` before live restore.
   - **Detection:** `grep -i vault /tmp/restore.log` after restore must be empty.

3. **Risk: Sequence values dump-time-correct but Aurora restore is hours later — INSERT after cutover collides on PK.**
   - **Likelihood:** LOW — most Prisma tables use UUID PKs (`gen_random_uuid()`), not sequences.
   - **Mitigation:** Section C.4 sequence-resync script runs unconditionally. Bumps every sequence to `MAX(id)+1` of its owning table.
   - **Detection:** First INSERT in smoke (Section E) catches this — duplicate-key error halts cutover before user traffic resumes.

4. **Risk: Lambda warm container keeps OLD env var (Supabase URL) past cutover.**
   - **Likelihood:** LOW — `update-function-configuration` recycles all warm containers within seconds.
   - **Mitigation:** Description-bump trick (Section D.4) is belt-and-suspenders. Smoke matrix detects via behavior (writes go to wrong DB).
   - **Detection:** Section E sentinel write to Aurora; if smoke selects same sentinel back from Aurora and DB row count matches, container is using new env.

5. **Risk: SG allowlist 0.0.0.0/0 left open post-cutover by mistake — Aurora exposed to internet credentials brute-force.**
   - **Likelihood:** MEDIUM — easy to forget the hardening step.
   - **Mitigation:** Add T+7:00 cutover step "tighten SG" (Section F.2) as MANDATORY runbook item. Aurora master password is 32-char auto-generated → brute-force resistant. IAM database authentication adds second factor.
   - **Detection:** Weekly CloudWatch alarm `LoginFailures > 10/5min` (Section G.1).

6. **Risk: Aurora bill spikes unexpectedly past $100/mo (e.g., due to a runaway Lambda loop opening connections, or unexpected ACU autoscale).**
   - **Likelihood:** LOW given 25 MB DB and small Lambda count, but non-zero.
   - **Mitigation:** Budget alarm at $80 actual + $100 forecast (Section G.2). ACU max=4 hard-caps compute spend at ~$345/mo even if pinned to ceiling 24×7.
   - **Detection:** Email alert + ACU saturation alarm.

7. **Risk: zietra-crm-api or zietra-api code REFERENCES `SUPABASE_URL` env var (despite no `@supabase/*` import) for some legacy auth flow we missed.**
   - **Likelihood:** LOW — CONTEXT.md grep verified zero imports, but env-var references could be string literals.
   - **Mitigation:** During dry-run (T-2h), `grep -rn "SUPABASE_URL\|SUPABASE_ANON_KEY\|SUPABASE_SERVICE_ROLE_KEY" /Users/jeet/doordash-p2p/<zietra-api-src>` to confirm. If found: keep those env vars (don't delete) and only flip the DB URL.
   - **Detection:** Smoke fails OR runtime errors in Lambda CloudWatch logs.

8. **Risk: `dollor/production/zietra-meet-8vOBAN` secret is read by an unaudited Lambda we didn't catalogue, breaking Meet booking.**
   - **Likelihood:** MEDIUM — CONTEXT.md flagged "verify which Lambda reads it; likely zietra-crm-api or unused".
   - **Mitigation:** Pre-cutover step: `aws lambda list-functions --region us-east-1 | jq -r '.Functions[].FunctionName' | xargs -I{} aws lambda get-function-configuration --function-name {} --query '{Name:FunctionName,Env:Environment.Variables}' --region us-east-1` then `grep zietra-meet`. If a Lambda outside our 4 reads it, expand scope or skip rotating that secret.
   - **Detection:** Pre-flight grep + smoke of Meet booking endpoint.

### H.2 Catastrophe-class risks (high-impact, worth calling out separately)

- **Catastrophe A: Wrong cluster identifier — provisioning eats `dollor-db` cluster.** Mitigation: identifier `zietra-aurora-prod` is distinct; CLI commands explicit. Manual eyeball before each `aws rds` command.

## I. State of the Art

| Old Approach | Current (2026) | Why Changed |
|--------------|----------------|-------------|
| Aurora Serverless v1 (separate engine) | Aurora Serverless v2 (provisioned + autoscale) | v1 deprecated; v2 = same engine as provisioned, scales seconds, supports min=0 since Nov 2024 |
| Lambda-VPC requires 10s cold start | Hyperplane ENI: <100ms penalty | AWS rearchitected ENIs in 2019; further refined 2025. ([AWS Compute blog](https://aws.amazon.com/blogs/compute/announcing-improved-vpc-networking-for-aws-lambda-functions/)) |
| RDS Proxy required for Lambda+Aurora | Optional; with Serverless v2 the 8-ACU minimum makes it expensive for small workloads | Strobes/dev.to cost-trap analyses circa 2025 |
| Aurora I/O-Optimized for everything | Standard for low-I/O, I/O-Optimized only when I/O > 25% bill | CloudFix break-even analysis; explicit cost difference $0.10 vs $0.225/GB storage |

**Deprecated/outdated:**
- Aurora Serverless v1 (no Postgres 16 support; no per-second billing for ramp-up)
- pg_dumpall for full migration (fails on hosted Postgres because pg_authid is restricted)
