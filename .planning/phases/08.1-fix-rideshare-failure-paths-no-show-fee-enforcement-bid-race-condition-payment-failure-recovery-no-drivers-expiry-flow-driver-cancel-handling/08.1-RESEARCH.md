## Summary

All five failure path problems have been researched against actual backend code.
The findings below are based on direct file:line verification — no guesswork.

**Critical discovery:** The bid race condition (problem 1) was already fixed in Quick-189
on 2026-03-18. `models.py:1459` has `UniqueConstraint('ride_request_id', 'driver_id')`,
`bid_routes.py:1375` has SELECT FOR UPDATE, and Alembic migration
`20260318_add_unique_constraint_ride_bid.py` is deployed. This problem is closed.

**Remaining problems are real and well-scoped:**
- No-show fee endpoint exists but does NOT charge Stripe — it only writes DB fields
- Payment capture failure is silently swallowed (`except Exception as e: logger.error(...)`)
- Bid expiry + no-drivers flow exists in the scheduler but sends no "retry/widen radius" UX
- Driver cancel is limited to MATCHED status only — cannot cancel IN_PROGRESS rides
- Android uses wrong endpoint path `v2/driver/rides/{id}/cancel` (dead ERP path) instead of `POST /api/rides/request/{id}/driver-cancel`

**Primary recommendation:** Three backend tasks (no-show Stripe charge, payment capture
retry, driver cancel IN_PROGRESS), one Android endpoint fix, one UX improvement to the
bid expiry push notification. No new models or migrations needed beyond the idempotency
key field for capture retries.

### Problem 2: No-Show Fee — Endpoint Exists, Stripe Charge Missing

**Backend endpoint:** `POST /api/rides/request/{request_id}/no-show`
File: `bid_routes.py:2058`

What the endpoint does today (verified):
1. Validates matched driver, MATCHED status, `driver_arrived_at` set, 5-minute wait enforced (`bid_routes.py:2073-2083`)
2. Sets `ride_request.status = CANCELLED` (`bid_routes.py:2086`)
3. Sets `ride_request.platform_fee = 5.00` and `ride_request.driver_payout = 4.00` (80%) in DB (`bid_routes.py:2090-2094`)
4. Sends push notification to customer (`bid_routes.py:2107-2120`)
5. Broadcasts WebSocket (`bid_routes.py:2126-2130`)

**What is missing:**
- No Stripe charge for the $5.00 no-show fee
- No cancellation of the pre-authorized PaymentIntent (the `capture_method="manual"` intent created at bid acceptance, `bid_routes.py:783`)
- No driver payout via Stripe Connect for their $4.00 compensation
- No email to customer documenting the charge

**iOS integration:** Fully wired (`P2PAPIService.swift:6557-6605`, `RideBiddingViewModel.swift:558-579`, `ActiveRideView.swift:529-533`). Timer starts on `.arrivedAtPickup` status, "Mark as No-Show" button appears at `noShowTimerSeconds <= 0`.

**Android integration:** No equivalent no-show method found in `DollorApiService.kt`. Android driver app does not have this functionality wired.

**Stripe pattern to follow:** Pre-auth intent created at `bid_routes.py:772-788` with `capture_method="manual"`. On no-show:
- Capture the pre-auth for the $5.00 fee amount (not the full fare)
- Or: cancel the original intent, create a new charge for $5.00
- Then: Stripe Connect transfer $4.00 to driver's `stripe_account_id` (same pattern as `complete_ride` at `bid_routes.py:2317`)

**The pre-auth intent was created for the full fare.** Stripe does not support partial capture from a `manual` intent to a different amount by default — the pre-auth must be cancelled and a separate `$5.00` charge created. OR the PaymentIntent amount can be updated before capture (Stripe supports `stripe.PaymentIntent.modify(pi_id, amount=500)` before capture).

### Problem 3: No Drivers / Bid Expiry Flow — Scheduler Exists, UX Incomplete

**Backend scheduler:** `check_ride_bidding_expiry_job()` at `bid_routes.py:3416`, registered in `order_flow.py:2924`.

What it does today:
- Runs every 60 seconds (`RIDE_CLEANUP_CHECK_INTERVAL_SECONDS = 60`)
- Finds OPEN/BIDDING rides with `bidding_expires_at < now`
- Sets status to `EXPIRED`
- Expires pending bids
- Sends push: "No Drivers Available — No drivers were available for your ride. Please try again." (`bid_routes.py:3453-3464`)

**What is missing:**
- Push notification has no deep-link or action data to send customer back to the booking screen
- No "widen radius" or "retry with adjusted price" prompt in the push payload
- No in-app notification created (uses push only; `_notify_customer()` not called)
- The EXPIRED status has no distinct customer-facing state machine on iOS/Android that prompts rebooking

**Key detail:** `bidding_expires_at` is set per-request at creation: `bidding_expires_at = datetime.utcnow() + timedelta(minutes=data.bidding_duration_minutes)` (`bid_routes.py:486`). Default is 5 minutes. The scheduler catches this correctly.

**Fix scope:** Push notification data needs `"action": "rebook"` key. iOS/Android customer apps need to handle `ride_expired` push type and navigate to the ride request screen. Backend may optionally add a retry endpoint.

### Problem 4: Driver Cancel After Accepting — Limited Scope

**Backend endpoint:** `POST /api/rides/request/{request_id}/driver-cancel`
File: `bid_routes.py:1964`

What it does today:
- Requires MATCHED status only (`bid_routes.py:1975`) — cannot cancel IN_PROGRESS rides
- Cancels the Stripe PaymentIntent (`bid_routes.py:1984`)
- Reverts ride to OPEN, clears `matched_driver_id` and `matched_at` (`bid_routes.py:1994-1998`)
- Expires matched bid (`bid_routes.py:2001-2009`)
- Sends push to customer ("We're finding you another driver") (`bid_routes.py:2023-2035`)
- No driver penalty, no cooldown, no repeat-cancel tracking

**Gap:** Driver cannot cancel once they tap "Start Ride" (status becomes IN_PROGRESS). There is no cancel endpoint for IN_PROGRESS status from driver side. The `check_ride_in_progress_timeout_job()` auto-cancels after 2 hours (`bid_routes.py:3652`), but there is no way for a driver to cancel mid-route through the app.

**Android endpoint mismatch — CRITICAL:**
Android's `DollorApiService.kt:702` calls `@POST("v2/driver/rides/{rideId}/cancel")`. This is the dead ERP path. The real endpoint is `POST /api/rides/request/{id}/driver-cancel`. This means Android drivers cannot cancel rides at all through the app.

**iOS:** Correctly uses `driverCancelRide(rideRequestId:reason:)` → `POST /api/rides/request/{id}/driver-cancel` (`P2PAPIService.swift:6264-6269`). Wired in `ActiveRideView.swift:171`.

**Fix scope:** Backend needs an IN_PROGRESS cancellation path. Android needs endpoint fix. Optionally: driver penalty system (track consecutive cancels, soft-block).

### Problem 5a: Payment Pre-Auth Failure (Stripe PaymentIntent creation fails at bid acceptance)

**Where it happens:** `bid_routes.py:749-790` — the `try/except` block after `db.commit()` at `bid_routes.py:747`.

Current behavior: If `stripe.PaymentIntent.create()` fails (network, invalid card, Stripe down), the error is caught and logged: `logger.error(f"Ride {ride_request.id} Stripe PaymentIntent creation failed (non-blocking): {e}")`. The ride proceeds to MATCHED status with `stripe_payment_intent_id = None`.

**Consequence:** The ride is MATCHED (driver en route) but there is no payment authorization. When `complete_ride()` runs at `bid_routes.py:2284`, the `if ride_request.stripe_payment_intent_id` check is `None`, so no capture happens, no payment occurs. Driver earns nothing from Stripe; the manual payout path is also skipped.

**Fix scope:**
- Option A: If PaymentIntent creation fails, revert ride to OPEN (don't match). Safest, but breaks flow if Stripe has transient issues.
- Option B: Mark `payment_intent_required = True` and retry asynchronously. On `complete_ride`, if no intent ID exists, create and immediately capture at that point.
- Option C: Pre-check customer has a valid saved payment method before allowing bid acceptance. Currently `Customer.stripe_customer_id` is created lazily.

### Problem 5b: Payment Capture Failure (Stripe capture fails after ride completion)

**Where it happens:** `bid_routes.py:2279-2294`

Current behavior:
```python
# bid_routes.py:2278-2294
try:
    stripe.PaymentIntent.capture(ride_request.stripe_payment_intent_id, ...)
    ride_request.payment_status = "captured"
    db.commit()
except Exception as e:
    logger.error(f"Ride {ride_request.id} PaymentIntent capture failed (non-blocking): {e}")
```

Ride is already `COMPLETED` (set at `bid_routes.py:2243` before the capture block). If capture fails:
- `payment_status` remains `None` (not "captured")
- `payment_completed_at` is not set
- No retry attempt
- No customer notification
- Driver payout still attempted (`bid_routes.py:2297`) — but `stripe.Transfer.create()` would fail too if the charge wasn't captured (transfer source would be invalid)

**Model field for tracking:** `payment_status` is a string column on `RideRequest` (verified at `bid_routes.py:2289`). Currently takes values: `"captured"`, `"demo"`, or `None`.

**Fix scope:**
- Add `payment_capture_failed_at` timestamp and `payment_retry_count` integer to `RideRequest`
- Background job: retry capture for rides where `status=COMPLETED` and `payment_status IS NULL` and `stripe_payment_intent_id IS NOT NULL`
- After N retries, flag for manual review, notify customer by email
- Block driver payout (`stripe.Transfer.create`) if capture has not succeeded

## Architecture Patterns

### Stripe Two-Phase: Authorize at Match, Capture at Complete

The system uses Stripe `capture_method="manual"`:
- **Create intent:** `bid_routes.py:772` — called when bid is accepted
- **Capture intent:** `bid_routes.py:2285` — called in `complete_ride()`
- **Cancel intent:** `bid_routes.py:1984` (driver cancel), `bid_routes.py:1098` (customer cancel)

This is correct for rideshare. The no-show fee needs a different amount — either `PaymentIntent.modify(amount=500)` before capture, or cancel + new charge.

### Scheduler Job Registration Pattern

All ride background jobs are defined in `bid_routes.py` and registered in `order_flow.py:2922-2944`. To add a new job:

```python
# In bid_routes.py — define the job function
def check_capture_retry_job():
    db = SessionLocal()
    try:
        ...
    except Exception as e:
        logger.error(...)
        db.rollback()
    finally:
        db.close()

# In order_flow.py — register it
from bid_routes import check_capture_retry_job
restaurant_timeout_scheduler.add_job(
    check_capture_retry_job,
    IntervalTrigger(seconds=300),  # every 5 min
    id="ride_capture_retry",
    name="Retry failed payment captures",
    replace_existing=True
)
```

### Alembic Migration Pattern

Existing migrations are in `apps/web/p2p-platform/backend/alembic/versions/`. The most
recent is `20260318_add_unique_constraint_ride_bid.py` with `down_revision = 'add_early_driver_notification'`.

## Common Pitfalls

### Pitfall 1: No-show Stripe Amount

The pre-auth intent was created for the full fare. Attempting to capture it for only $5.00 requires `stripe.PaymentIntent.modify(intent_id, amount=500)` BEFORE calling `capture()`. If you call `capture(amount=500)` directly without `modify()`, it will fail if the intent was authorized for more than $5.00 with partial capture not enabled. **Safest path:** Cancel the pre-auth intent, create a fresh `$5.00` PaymentIntent, confirm it immediately (requires a saved payment method on the customer). Requires `Customer.stripe_customer_id` to exist.

### Pitfall 2: Driver Cancel — MATCHED vs IN_PROGRESS

The current `driver_cancel_ride()` only accepts `MATCHED` status at `bid_routes.py:1975`. If you extend it to accept `IN_PROGRESS`, you must also handle:
- The PaymentIntent is already in `requires_capture` state (pre-auth from bid acceptance). Cancelling it releases the hold on the customer.
- If a cancellation fee should apply to the customer (driver abandoned mid-route), you cannot use the same `PaymentIntent.cancel()` path — you need to capture a fee amount instead.
- The driver payout should be $0 or partial, depending on policy.

### Pitfall 3: Capture Retry — Idempotency Key Collision

The existing capture call uses `idempotency_key=f"ride-capture-{ride_request.id}"` at `bid_routes.py:2287`. Retrying with the same key is idempotent — Stripe will return the same result. This is the correct behavior. Do NOT change the idempotency key on retry.

### Pitfall 4: Android Endpoint Path Mismatch

`DollorApiService.kt:702` has `@POST("v2/driver/rides/{rideId}/cancel")`. The `v2` prefix is the old ERP API that was removed (Quick-54). The real path is `rides/request/{rideId}/driver-cancel` relative to base URL `https://api.dollor.ai/api/`. This has been a silent failure — Android drivers calling cancel get 404 and the error is likely swallowed.

### Pitfall 5: Bid Expiry Push — Missing Action Key

The current `ride_expired` push at `bid_routes.py:3453-3464` sends `{"type": "ride_expired", "ride_id": ..., "ride_request_id": ...}`. The iOS customer app `eatfaircustomerApp.swift:172` only handles `.driverArrived`, `.rideStarted`, `.rideCompleted`, `.rideCancelled`, `.driverEnRoute` in the navigation switch. The `ride_expired` type is not handled — the push appears but tapping it does nothing. Need to add handling on both iOS and Android.

## Code Examples

### No-Show Fee: Cancel Pre-Auth + New Charge Pattern

```python
# Source: bid_routes.py:2058 (existing endpoint, extend this)
# Step 1: Cancel the pre-authorized PaymentIntent (full fare amount)
if ride_request.stripe_payment_intent_id and not ride_request.stripe_payment_intent_id.startswith("demo_"):
    stripe.PaymentIntent.cancel(
        ride_request.stripe_payment_intent_id,
        idempotency_key=f"ride-noshow-cancel-{ride_request.id}"
    )
    ride_request.stripe_payment_intent_id = None

# Step 2: Charge the $5.00 no-show fee via a new PaymentIntent
customer_obj = db.query(Customer).filter(Customer.id == ride_request.customer_id).first()
if customer_obj and customer_obj.stripe_customer_id:
    fee_intent = stripe.PaymentIntent.create(
        amount=500,  # $5.00 in cents
        currency="usd",
        customer=customer_obj.stripe_customer_id,
        description=f"No-show fee — Ride {ride_request.request_id}",
        confirm=True,
        off_session=True,  # customer not present
        idempotency_key=f"ride-noshow-fee-{ride_request.id}"
    )
    ride_request.stripe_payment_intent_id = fee_intent.id
    ride_request.payment_status = "captured"
```

## Open Questions

1. **No-show: off_session charge requires saved payment method**
   - What we know: `Customer.stripe_customer_id` is created lazily at bid acceptance time (`bid_routes.py:760-767`)
   - What's unclear: Does every customer who gets matched have a `stripe_customer_id`? What if the customer has no saved payment method on the Stripe customer object?
   - Recommendation: Verify at no-show time; if no saved method, skip Stripe charge but still cancel the pre-auth and log for manual follow-up. Don't block the no-show flow.

2. **Driver cancel penalty policy**
   - What we know: No penalty exists currently
   - What's unclear: What is the desired penalty? Soft-block after N cancels? Fine?
   - Recommendation: Start with no penalty for Phase 8.1; add penalty tracking as a separate phase if needed.

3. **IN_PROGRESS driver cancel: customer charge policy**
   - What we know: Rider was picked up; driver abandoning mid-route is severe
   - What's unclear: Should the customer pay a partial fare? Full fare? No charge?
   - Recommendation: Default to no charge (cancel intent, no transfer). Full refund. Flag for manual review.
