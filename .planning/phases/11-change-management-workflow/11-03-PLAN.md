<task type="auto">
  <name>Task 2: Wire notifications into lifecycle transitions and add CI approval check</name>
  <files>apps/web/p2p-platform/backend/change_management.py</files>
  <action>
Update the existing API routes in change_management.py to call notification functions at the right lifecycle points:

**Email notifications (critical transitions only):**
- `submit` route (Submitted -> Under Review): Call `send_approval_needed_email()` to department lead. Implement batch throttling: maintain an in-memory dict `_pending_approvals: dict[str, list[tuple[str, datetime]]]` keyed by lead_email. If 3+ CRs submitted for same lead within 5 minutes, call `send_approval_digest_email()` instead of individual emails. Clear entries older than 5 minutes on each call.
- `reject` route: Call `send_cr_rejected_email()` to requested_by
- `transition` route when new_status="CI Running" and ci_status="failed": Call `send_ci_failed_email()` to requested_by
- `transition` route when new_status="Staging": Call `send_deploy_complete_email()` with environment="staging" to requested_by
- `transition` route when new_status="Production": Call `send_deploy_complete_email()` with environment="production" to requested_by
- `rollback` route: Call `send_rollback_triggered_email()` to requested_by of the original CR

**WebSocket notifications (all transitions):**
- In every route that changes status, call `broadcast_cm_event()` with the event type and CR data AFTER the db.commit() succeeds. Do NOT broadcast inside the transaction.

**CI Approval Check Endpoint:**
Add `GET /api/admin/change-requests/{cr_id}/ci-check` endpoint:
- Returns JSON: `{ "approved": bool, "approved_by": str|null, "approved_at": str|null, "cr_id": str, "status": str }`
- CI pipeline can call this to verify a PR's associated CR was properly approved before allowing merge
- Returns 404 if CR not found, 200 with approved=false if not yet approved

**Stale Check Helper:**
Add a function `get_stale_requests(db, timeout_minutes=30)` that returns CRs stuck in "CI Running" or "Staging" for longer than timeout_minutes. This is a query helper the admin portal can call. Add `GET /api/admin/change-requests/stale` endpoint exposing it. Used for monitoring -- flags requests that might need manual intervention.

Wrap all email sends in try/except so a failed email never breaks a lifecycle transition. Log the error but don't raise.
