## Summary

This phase moves Zietra Platform from "demo-grade public-internet AWS" to "enterprise-conversation-ready AWS" through five interlocking changes: (1) build a fresh private VPC, (2) migrate Aurora into it via snapshot+restore (in-place modify-db-cluster across VPCs is NOT supported — AWS docs are explicit: "Updating VPCs isn't currently supported for Aurora DB clusters"), (3) attach all 4 Lambdas to the VPC, (4) front Aurora with RDS Proxy using IAM auth, (5) close the long-standing 0.0.0.0/0:5432 SG gap deferred from Phase 54.5-03. Layered on top: WAF on every CloudFront distribution, GuardDuty + Security Hub + AWS Config for continuous posture monitoring, and a public `/security` page at zietra.com summarizing the controls.

**Primary recommendation: 4 plans, executed sequentially with one gate.**

- **54.6-01** (autonomous-with-gate): VPC + subnets + NAT + Aurora snapshot+restore-to-new-cluster into the new VPC. Gate before cutover: operator GO/NO-GO after dry-run snapshot test.
- **54.6-02** (autonomous): RDS Proxy + Lambda VPC-attach + connection-string flip + Aurora SG hardening (close 0/0:5432).
- **54.6-03** (fully autonomous): WAF (single shared ACL across 3 distros, COUNT mode for 24h then BLOCK) + GuardDuty + Security Hub + AWS Config + initial findings triage.
- **54.6-04** (fully autonomous): zietra.com/security trust page + full cross-cutting smoke matrix + Phase 55/M3 CHECKPOINT.md handoff.

**Three critical facts the planner MUST honor:**

1. **In-place Aurora VPC migration is NOT possible** — DB subnet group is bound to a single VPC ([AWS docs](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html): "Updating VPCs isn't currently supported for Aurora DB clusters"). Use snapshot → restore-into-new-VPC. Keep old cluster for 7-day rollback before deleting.
2. **RDS Proxy on Aurora Serverless v2 = $144/mo minimum** (8 ACU × $0.025/ACU-hr × 730 hrs). This is locked per ROADMAP and accepted as the cost of enterprise hardening; in 54.5 it was rejected at this same price because Lambdas weren't VPC-attached. In 54.6 we ARE VPC-attaching, so Proxy adds IAM-auth + connection-pool + failover-transparency on top of a sunk-cost VPC migration.
3. **VPC-attached Lambda cold-start penalty is <100ms** post-Hyperplane-ENI ([AWS Compute blog](https://aws.amazon.com/blogs/compute/announcing-improved-vpc-networking-for-aws-lambda-functions/), confirmed by [2025 cold-start optimization article](https://zircon.tech/blog/aws-lambda-cold-start-optimization-in-2025-what-actually-works/) — "VPC adds under 50ms and rarely affects cold starts unless heavy networking runs during INIT"). The pre-2019 multi-second penalty is gone. Acceptable for our demo workload.

**Total estimated monthly cost delta:** ~$240/mo (NAT $32 + RDS Proxy $144 + WAF $25 + GuardDuty $30 + Security Hub $10 + Config $15 + per-request charges ≈ $5).

## A. VPC + Subnets + Routing + NAT

### A.1 Subnet CIDR allocation

| Subnet | CIDR | AZ | Role | Routes to |
|--------|------|----|----|-----------|
| `zietra-prod-public-1a` | `10.0.0.0/24` | us-east-1a | Public — NAT GW + Bastion if added | IGW |
| `zietra-prod-public-1b` | `10.0.1.0/24` | us-east-1b | Public — reserved for HA NAT (M8) | IGW |
| `zietra-prod-private-1a` | `10.0.10.0/24` | us-east-1a | Private — Lambdas + Aurora primary | NAT (via public-1a route table) |
| `zietra-prod-private-1b` | `10.0.11.0/24` | us-east-1b | Private — Aurora replica + Lambda HA | NAT (via public-1a route table — single NAT for now) |

**256 IPs per /24 minus 5 AWS-reserved = 251 usable per subnet.** Plenty of headroom: each Lambda invocation consumes ~1 IP (shared Hyperplane ENI per subnet+SG combo, not per-invocation). Aurora needs 2-3 IPs per AZ. RDS Proxy needs 1-2 IPs per AZ.

**Confirmed structure** — matches [AWS RDS VPC tutorial](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/CHAP_Tutorials.WebServerDB.CreateVPC.html) recommended layout. The "two private DB subnets in two AZs" pattern is mandatory: Aurora's DB subnet group requires subnets in ≥2 AZs even if we run a single writer.

### A.2 IaC recommendation: pure `aws` CLI

ROADMAP §54.6 said "Terraform OR aws CLI shell scripts." Recommend **pure `aws` CLI in `scripts/setup-vpc-and-private-aurora.sh`** for these reasons:

1. **Consistency with prior infra.** All prior AWS infra in Zietra Platform (Phases 35-54.5) was provisioned via `aws` CLI scripts (`./build-and-push.sh`, `./deploy-frontend.sh`, `scripts/provision-cognito-groups-phase54-1.sh`). Adding Terraform now bifurcates the operational mental model.
2. **One-shot provisioning.** VPCs aren't iterated — once provisioned, the only ongoing operations are SG rule modifications (better done via CLI for atomicity). No Terraform state file = no drift detection burden.
3. **Reversibility.** A CLI script is line-by-line auditable in the runbook. Terraform diff requires `tf plan` against a separate state.

If we later need IaC discipline for multi-region or multi-account, that's an M8 retrofit.

### A.3 VPC creation commands

```bash
#!/bin/bash
set -euo pipefail
REGION=us-east-1
AWS_ACCOUNT=134607809447

# 1. Create VPC
VPC_ID=$(aws ec2 create-vpc \
  --cidr-block 10.0.0.0/16 \
  --tag-specifications "ResourceType=vpc,Tags=[{Key=Name,Value=zietra-prod-vpc},{Key=Phase,Value=54.6},{Key=Environment,Value=production}]" \
  --region $REGION --query 'Vpc.VpcId' --output text)
echo "VPC: $VPC_ID"

# Enable DNS hostnames + resolution (REQUIRED for RDS Proxy DNS to resolve from Lambdas)
aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-hostnames --region $REGION
aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-support --region $REGION

# 2. Internet Gateway (for public subnets + NAT egress)
IGW_ID=$(aws ec2 create-internet-gateway \
  --tag-specifications "ResourceType=internet-gateway,Tags=[{Key=Name,Value=zietra-prod-igw}]" \
  --region $REGION --query 'InternetGateway.InternetGatewayId' --output text)
aws ec2 attach-internet-gateway --vpc-id $VPC_ID --internet-gateway-id $IGW_ID --region $REGION

# 3. Four subnets across 2 AZs
PUB_1A=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID --cidr-block 10.0.0.0/24 --availability-zone us-east-1a \
  --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=zietra-prod-public-1a},{Key=Tier,Value=public}]" \
  --region $REGION --query 'Subnet.SubnetId' --output text)
PUB_1B=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID --cidr-block 10.0.1.0/24 --availability-zone us-east-1b \
  --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=zietra-prod-public-1b},{Key=Tier,Value=public}]" \
  --region $REGION --query 'Subnet.SubnetId' --output text)
PRIV_1A=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID --cidr-block 10.0.10.0/24 --availability-zone us-east-1a \
  --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=zietra-prod-private-1a},{Key=Tier,Value=private}]" \
  --region $REGION --query 'Subnet.SubnetId' --output text)
PRIV_1B=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID --cidr-block 10.0.11.0/24 --availability-zone us-east-1b \
  --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=zietra-prod-private-1b},{Key=Tier,Value=private}]" \
  --region $REGION --query 'Subnet.SubnetId' --output text)
echo "Subnets: pub1a=$PUB_1A pub1b=$PUB_1B priv1a=$PRIV_1A priv1b=$PRIV_1B"

# 4. NAT Gateway — sits in public-1a (single AZ, HA NAT deferred to M8)
EIP_ALLOC=$(aws ec2 allocate-address --domain vpc \
  --tag-specifications "ResourceType=elastic-ip,Tags=[{Key=Name,Value=zietra-prod-nat-eip}]" \
  --region $REGION --query 'AllocationId' --output text)
NAT_ID=$(aws ec2 create-nat-gateway \
  --subnet-id $PUB_1A --allocation-id $EIP_ALLOC \
  --tag-specifications "ResourceType=natgateway,Tags=[{Key=Name,Value=zietra-prod-nat}]" \
  --region $REGION --query 'NatGateway.NatGatewayId' --output text)
echo "NAT GW: $NAT_ID (wait ~3 min for available)"
aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT_ID --region $REGION

# 5. Route tables
# Public RT: default route → IGW
PUB_RT=$(aws ec2 create-route-table --vpc-id $VPC_ID \
  --tag-specifications "ResourceType=route-table,Tags=[{Key=Name,Value=zietra-prod-public-rt}]" \
  --region $REGION --query 'RouteTable.RouteTableId' --output text)
aws ec2 create-route --route-table-id $PUB_RT --destination-cidr-block 0.0.0.0/0 \
  --gateway-id $IGW_ID --region $REGION
aws ec2 associate-route-table --route-table-id $PUB_RT --subnet-id $PUB_1A --region $REGION
aws ec2 associate-route-table --route-table-id $PUB_RT --subnet-id $PUB_1B --region $REGION

# Private RT: default route → NAT GW
PRIV_RT=$(aws ec2 create-route-table --vpc-id $VPC_ID \
  --tag-specifications "ResourceType=route-table,Tags=[{Key=Name,Value=zietra-prod-private-rt}]" \
  --region $REGION --query 'RouteTable.RouteTableId' --output text)
aws ec2 create-route --route-table-id $PRIV_RT --destination-cidr-block 0.0.0.0/0 \
  --nat-gateway-id $NAT_ID --region $REGION
aws ec2 associate-route-table --route-table-id $PRIV_RT --subnet-id $PRIV_1A --region $REGION
aws ec2 associate-route-table --route-table-id $PRIV_RT --subnet-id $PRIV_1B --region $REGION

echo "VPC ready: $VPC_ID"
echo "PRIVATE_SUBNETS=\"$PRIV_1A,$PRIV_1B\""
echo "PUBLIC_SUBNETS=\"$PUB_1A,$PUB_1B\""
```

**Wall-time:** ~5 min (NAT GW wait dominates at 2-3 min).

**Cost (NAT GW):** `$0.045/hr × 730 hrs = $32.85/mo` + `$0.045/GB processed` ([NAT GW pricing](https://aws.amazon.com/vpc/pricing/)). At our traffic (~10 GB/mo Lambda-to-internet for Cognito/SES/Anthropic), processing fee is ~$0.45/mo. **Total: ~$33/mo.**

## B. Aurora Private Migration (snapshot+restore)

### B.1 The critical AWS constraint

**Direct quote from AWS docs** ([USER_VPC.WorkingWithRDSInstanceinaVPC.html](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html)):

> **Note: Updating VPCs isn't currently supported for Aurora DB clusters.**

This applies to changing the DB subnet group across VPCs. You CAN modify which subnet group is attached, but the new subnet group must be in the same VPC. To move to a new VPC, you MUST snapshot and restore.

**Implication:** ROADMAP §54.6 said "prefer in-place modify-db-cluster; fallback to snapshot+restore." Reality is the fallback IS the primary path. Plan accordingly.

### B.3 Snapshot + restore to new VPC

```bash
# 1. Take final snapshot of current cluster (NOT manual; use latest automated or create manual)
SNAP_ID=zietra-aurora-pre-vpc-migration-$(date +%Y%m%d-%H%M%S)
aws rds create-db-cluster-snapshot \
  --db-cluster-identifier $OLD_CLUSTER \
  --db-cluster-snapshot-identifier $SNAP_ID \
  --region us-east-1
aws rds wait db-cluster-snapshot-available \
  --db-cluster-snapshot-identifier $SNAP_ID --region us-east-1
echo "Snapshot ready: $SNAP_ID"

# 2. Create new DB subnet group in zietra-prod-vpc
aws rds create-db-subnet-group \
  --db-subnet-group-name zietra-aurora-private-subnets \
  --db-subnet-group-description "Zietra Aurora in zietra-prod-vpc private subnets" \
  --subnet-ids $PRIV_1A $PRIV_1B \
  --region us-east-1

# 3. Restore cluster from snapshot INTO the new VPC subnet group
NEW_CLUSTER=zietra-aurora-prod-v2
aws rds restore-db-cluster-from-snapshot \
  --db-cluster-identifier $NEW_CLUSTER \
  --snapshot-identifier $SNAP_ID \
  --engine aurora-postgresql \
  --engine-version 16.4 \
  --db-subnet-group-name zietra-aurora-private-subnets \
  --vpc-security-group-ids $AURORA_NEW_SG \
  --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=4 \
  --enable-iam-database-authentication \
  --enable-cloudwatch-logs-exports '["postgresql"]' \
  --no-publicly-accessible \
  --region us-east-1

aws rds wait db-cluster-available --db-cluster-identifier $NEW_CLUSTER --region us-east-1

# 4. Create writer instance in restored cluster (restore creates the cluster but no instance)
aws rds create-db-instance \
  --db-cluster-identifier $NEW_CLUSTER \
  --db-instance-identifier ${NEW_CLUSTER}-writer \
  --db-instance-class db.serverless \
  --engine aurora-postgresql \
  --no-publicly-accessible \
  --region us-east-1
aws rds wait db-instance-available --db-instance-identifier ${NEW_CLUSTER}-writer --region us-east-1

# 5. New cluster endpoint
NEW_ENDPOINT=$(aws rds describe-db-clusters --db-cluster-identifier $NEW_CLUSTER \
  --query 'DBClusters[0].Endpoint' --output text --region us-east-1)
echo "New private endpoint: $NEW_ENDPOINT"
# → zietra-aurora-prod-v2.cluster-XXXXX.us-east-1.rds.amazonaws.com (resolves to private IP)
```

**Wall-time:** snapshot ~5 min (at 25 MB), restore ~8 min, instance create ~5 min, total ~18 min.

**Master password:** Snapshot+restore PRESERVES the master password from the source cluster. The Secrets Manager secret `rds!cluster-8dac9fc2-…` keeps working IF you set `--manage-master-user-password` on restore. Alternative: explicit `--master-user-password $OLD_PW` if you have it in hand. Recommend `--manage-master-user-password` to keep the same rotation mechanism.

**Acceptance:** diff returns 0 lines. If non-empty, HALT and triage.

### B.5 Cutover decisions

**Read-only window during cutover:** Yes. The snapshot is taken at T0, and any writes between T0 and Lambda env-var flip would be lost on the new cluster. Options:

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| (A) Brief read-only window during low-traffic hour (e.g., 4 AM UTC) | Simple, zero data loss risk | ~15-30 min of write-disabled state — fine for demo, painful in prod | **Pick this** |
| (B) Logical replication from old to new | Zero downtime | Massive complexity for 25 MB DB, replication slot management, no real benefit | Skip |
| (C) Hot snapshot + accept tiny drift | Fast | Demos can write during snap — drift = real bug | Skip |

**Read-only enforcement:**
```sql
-- On old cluster, just before snapshot:
ALTER DATABASE zietra SET default_transaction_read_only = on;
-- Restart pg_pool or app to pick up. Easier: revoke INSERT/UPDATE/DELETE from app role.
-- For 25MB DB with 4 demo Lambdas, simpler: ride a 5-min window where you don't touch traffic
-- and rely on demo-grade traffic being effectively zero in off-hours.
```

**Pragmatic recommendation:** Snapshot at 03:00 UTC (low traffic), complete restore + Lambda flip by 03:30 UTC, total write-loss window <30 min for traffic that is effectively zero anyway. Document in runbook.

### B.6 Old cluster retention

Per ROADMAP: "old cluster kept for 7-day rollback before deleting."

Keep `zietra-aurora-prod` running on its existing Aurora compute through **2026-05-29** (14 days post-cutover, exceeding the 7-day minimum to allow for any soak issues caught late). Cost during retention: ~$45/mo prorated to ~$21 for 14 days. After 2026-05-29: `delete-db-cluster --skip-final-snapshot` (we already have a final snapshot from B.3).

**Rollback decision tree (if 54.6 needs to revert):**

| Trigger | Within 24h | Days 1-7 | Days 7-14 |
|---------|------------|----------|-----------|
| Lambda write failures | Roll Lambda env vars back to OLD_ENDPOINT (still up) | Same | Same — old cluster still up |
| Parity drift detected | Re-snapshot new cluster + ad-hoc diff | Same | Same |
| Cost spike beyond budget | Resize down or rollback | Same | Replan |

After 2026-05-29: rollback requires restoring from the **final pre-migration snapshot** (taken in B.3) into a fresh cluster. Adds ~20 min RTO but covers indefinitely.

**Mitigation:** Attach Lambdas one at a time, with smoke test after each. First Lambda's first invocation may be slow (one-time provision); all subsequent Lambdas + invocations benefit from the warmed ENIs.

## D. RDS Proxy

### D.1 Cost reality

**Per AWS docs ([RDS Proxy Pricing](https://aws.amazon.com/rds/proxy/pricing/)):** RDS Proxy on Aurora Serverless v2 is priced "per Aurora Capacity Unit (ACU) per hour consumed by your database."

**Per industry analysis ([Dev.to cost trap analysis](https://dev.to/aws-builders/caught-in-a-cost-optimization-trap-aurora-serverless-v2-with-rds-proxy-2mng)):** "RDS Proxy for Aurora Serverless v2 incurs a minimum charge for 8 ACUs. (24 hrs/day) × (30 days/month) × ($0.025/ACU hr) × 8 ACU = **$144/month**."

This is the same number Phase 54.5 RESEARCH §B.3 used to skip RDS Proxy. **In Phase 54.6 we accept the cost** because:
1. We're VPC-attaching Lambdas anyway (the operational reason 54.5 declined Proxy is gone).
2. Proxy adds IAM authentication — no static password in app config.
3. Proxy makes Aurora Serverless v2 failover transparent to Lambdas.
4. Connection pool isolation prevents Lambda concurrency from exhausting Aurora's connection limit at scale-up.
5. $144/mo is justifiable as "enterprise hardening cost" — same line item as WAF, GuardDuty, Config in the $240/mo total.

### E.4 Soak window + switch to BLOCK

**Soak protocol:**
- T+0: ACL associated, rules in COUNT mode. Metrics flow to CloudWatch.
- T+24h: review CloudWatch metrics for each rule. False-positive identification:
  - **Counted requests on legitimate paths** (e.g., `/api/auth/callback`, magic-link redirects with long tokens)
  - **Bot Control flags on legitimate health checks** (CloudFront origin probes, status pages)
  - Set IP exception or custom rule with `Priority` lower than the flagging rule, action `Allow`.
- T+24h+: For each rule that shows zero false positives, switch `OverrideAction` to `None` (= use rule's default action, which is BLOCK for most managed groups).

```bash
# Update OverrideAction to None for one rule at a time, after metric review
# Example: switch CRS to BLOCK

  --region us-east-1 > /tmp/current-acl.json
# Edit /tmp/current-acl.json: remove "OverrideAction": {"Count": {}} from the rule (or replace with {"None":{}})
aws wafv2 update-web-acl \
  --scope CLOUDFRONT --id <acl-id> --name zietra-prod-waf \
  --rules file:///tmp/updated-rules.json \
  --default-action Allow={} \
  --visibility-config '...' \
  --lock-token <lock-token-from-get>
```

**Sequencing recommendation:** Switch one rule per day in this order — Known Bad Inputs (lowest FP rate) → IP Reputation → Common Rule Set (highest FP rate, watch carefully) → Bot Control Common (last because demo URLs aren't bot-targeted).

### E.5 False-positive playbook

The single biggest WAF risk is blocking legitimate Cognito hosted-UI callbacks (JWT tokens look like injection payloads to naive rules) or magic-link redirects (long Base64 query strings).

**Known triggers from prior phases:**
- Phase 41 Cognito hosted-UI callback uses `code` query param (no risk)
- Phase 41 `id_token` in fragment (no risk — fragment never hits server)
- Phase 39 magic-link signed URLs have base64-ish tokens (LOW risk on KBI)
- Phase 52 `/api/tenants/signup` POST body has email/password JSON (no risk on standard JSON)

**Pre-add allowlist for known false-positive paths:**
