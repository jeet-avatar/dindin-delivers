## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] marquee.zietra.com + asc606.zietra.com don't live on CloudFront**
- **Found during:** Task 1, runtime discovery via DNS + headers
- **Issue:** Plan's `must_haves.truths` line 26 expected "Web ACL ASSOCIATED with 3 CloudFront distributions: turionspace, marquee, asc606". Reality: marquee + asc606 resolve directly to APIGW v2 IPs, NOT CloudFront. Memory confirms shape: `AWS Lambda + APIGW + ACM` for both — no CF layer.
- **Fix:** Attached CF ACL to the **2 real CF distros** (turion E37R9PT8IL44L2 + zietra-apex E1X82T89JWL8CA — discovered the apex distro during enumeration). Created REGIONAL ACL with same rule set for future use. Discovered secondary blocker: both marquee/asc606 use APIGW v2 (HTTP API), which WAFv2 does NOT support — only REST API v1. REGIONAL ACL therefore stays UNATTACHED.
- **Coverage outcome:** turion + zietra-apex PROTECTED; marquee + asc606 UNPROTECTED at edge (native APIGW v2 controls still in place — throttling, JWT authorizers).
- **Follow-up:** Option A (front each APIGW v2 with new CF distro) documented in runbook as preferred; Option C (native APIGW v2 controls) acceptable for demo phase.
- **Committed in:** Task 1 (`ce727d6a`)

**2. [Rule 3 - Blocking] WAFv2 associate-web-acl rejects CloudFront ARNs**
- **Found during:** Task 1, first associate attempt
- **Issue:** Plan's action block used `aws wafv2 associate-web-acl --resource-arn arn:aws:cloudfront::ACCT:distribution/...` which returned `WAFInvalidParameterException: The ARN isn't valid`.
- **Root cause:** WAFv2's associate-web-acl supports ONLY REGIONAL targets (REST API, ALB, AppSync, Cognito UserPool, App Runner, Amplify, Verified Access). CloudFront uses a different attachment mechanism.
- **Fix:** Rewrote script section to use `cloudfront update-distribution` setting `DistributionConfig.WebACLId` to the WAFv2 ACL ARN. Uses get-distribution-config → jq patch → update-distribution with ETag.
- **Verification:** Both CF distros now have WebACLId set, Status=Deployed, smoke 2/2 PASS.
- **Committed in:** Task 1 (`ce727d6a`)

**3. [Rule 3 - Blocking] AWS Config service-linked role NOT auto-created**
- **Found during:** Task 3, post-PutConfigurationRecorder verification (lastStatus=FAILURE)
- **Issue:** Config recorder cannot assume `AWSServiceRoleForConfig`. The role doesn't exist; sandbox blocks ALL `aws iam` commands including `create-service-linked-role`.
- **Root cause:** Phase 54.6-02 pattern allowed `put-role-policy` (write inline policy) but did NOT establish a workaround for `create-service-linked-role` / `create-role`. CloudTrail shows GuardDuty/Security Hub/Config-Conforms successfully triggered SLR auto-creation (the service action does it internally) — but Config's PutConfigurationRecorder does NOT trigger SLR creation.
- **Fix (partial):** Recorder + S3 + delivery channel + conformance pack all configured correctly; lastStatus=FAILURE remains until operator runs ONE command from IAM-admin credentials (NOT the CRMaccesskey executor):
  ```bash
  aws iam create-service-linked-role --aws-service-name config.amazonaws.com
  ```
  Then re-run `scripts/provision-aws-config.sh` (idempotent — restarts recorder).
- **Non-blocking for Wave 3:** Config FAILURE state doesn't affect GuardDuty + Security Hub + WAF coverage. Conformance pack rules will start evaluating only after recorder leaves FAILURE state.
- **Operator action item:** Documented prominently at top of `waf-deployment-54-6-03.md` Config section.
- **Committed in:** Task 3.b (`d66fa353`)
