## Decisions Made

1. **PUBLIC endpoint in separate router file.** `routes/team.ts` applies `tenantContext+requireAuth` at the `r.use(...)` level — the only safe way to keep `accept-invite` PUBLIC is its own file (`routes/invites.ts`) mounted at its own path (`/api/invites`). Mounting under `/api/team` and trying to selectively skip middleware would be fragile.
2. **Best-effort SES (CONTEXT.md autonomous mode).** Wrap `await sendEmail(...)` in try/catch + console.warn. Sandbox failure on unverified recipients = logged warning, request still 200, invite row exists. Inviter can manually relay the URL.
3. **Idempotent invite via SELECT-then-UPDATE-or-INSERT.** Not `ON CONFLICT DO UPDATE` — we want distinct error messages for `active` (409 'Already a member'), `suspended` (409 'Member is suspended'), `removed` (409 'Member was removed; re-invite blocked'), and `pending` (UPDATE token+expiry+role).
4. **Generic 410 on accept-invite (no info leak).** Both invalid token and expired token return `'Invite expired or already used'` — defeats token enumeration probes.
5. **Lowercase group name.** `groupName = row.role.toLowerCase()` before `AdminAddUserToGroupCommand` — DB CHECK enforces lowercase but defense-in-depth.
6. **TypeScript `unknown` + `instanceof Error`.** Matches Plan 54.1-01's convention — avoids `@typescript-eslint/no-explicit-any` warnings; functionally equivalent to `e: any + e?.message`.

## Deviations from Plan

### Smoke-test status-code interpretation (clarification, not deviation)

The plan's smoke section said "expect 401" for the 4 team endpoints with no auth. Without an `X-Tenant-Slug` header, the actual response is **400** (`Missing X-Tenant-Slug header`) because `tenantContext` runs FIRST in the router middleware chain (per Phase 53 contract) — the request never reaches `requireAuth`.

To prove `requireAuth` is wired correctly, I ran a SECOND smoke pass with `X-Tenant-Slug: turion` and no Bearer token:

```
GET /api/team           (slug, no bearer): 401  body={"error":"Missing authorization token"}
POST /api/team/invite   (slug, no bearer): 401
PATCH /api/team/zzz/role(slug, no bearer): 401
DELETE /api/team/zzz    (slug, no bearer): 401
```

This is the correct middleware order (tenantContext → requireAuth → requireRole) and matches the Phase 53 documented behavior. The plan's "expect 401" was a one-step short-cut; both 400-without-slug and 401-with-slug-no-bearer are correct.
