## Decisions Made

See `key-decisions` in frontmatter. Highlights:

1. **Ground-truth schema verification BEFORE coding** — The plan's sample SQL referenced `source_data->>'type'` for the BS class grouping. Live probe via `zietra-rls-runner-55-05` revealed the actual field is `source_data->>'class'` (values: Asset/Liability/Equity/Revenue/Expense/Pool/Other/Suspense). Adapted accordingly. This is exactly what the deviation Rule-1 (bug) rule exists for — but it was caught *before* writing code, so no rework needed.

2. **BS uses gl_accounts.balance, NOT JE recomputation** — The seed has running balances on gl_accounts. Rebuilding from JEs would massively under-report (only 20 JEs cover ~9 periods; the real activity is far larger). The `period` param is accepted for API symmetry but doesn't filter — frontend pages can display it as a label.

3. **PL uses paired-leg interpretation** — Each JE has ONE `amount` posted as both a debit AND a credit to two accounts. For PL we sum that amount where (credit-side account is Revenue) OR (debit-side account is Expense). This matches GAAP normal balance conventions.

4. **Period-close 16 steps are process metadata** — Identical labels across tenants (NetSuite-standard close workflow). Status varies by tenant's je_count for the period. Frontend `netsuite-financials.html:273-288` hardcoded "14 of 16 done" — our derived status produces exactly that for any tenant with JEs in the period.

5. **Lambda deploy is INSIDE the plan task per CLAUDE.md** — Not ad-hoc. Pre-deploy push to origin first (push-before-deploy rule). Stashed parallel-agent's uncommitted changes BEFORE building so my Lambda image is clean.
