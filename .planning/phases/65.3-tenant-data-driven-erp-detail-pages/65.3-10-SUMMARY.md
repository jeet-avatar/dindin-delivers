## Decisions Made

1. **Wrap inner content, not the container itself.** `.ns-content`, `.arena-main`, sf-panels — these are addressed by `document.querySelector(...)` calls in renderer JS (e.g., `renderListView()` in customer-so, `renderListView()` in items, the BOM tree renderer in arena-bom, the SF tab switcher). If the shim removes the container, the renderer breaks. Wrap one extra `<div data-tenant-only="turion">` INSIDE the container instead — keeps the shell, removes the narrative.

2. **Per-panel gating for salesforce-account.** salesforce-account has 7 sf-panels (accounts/home/contacts/opportunities/contracts/cases/reports). A single mega-wrapper would have hidden the entire SF UI for non-Turion. Per-panel wrapping gives each panel its own empty-state and keeps the tab navigation chrome rendering correctly (the tab list itself is universal SF chrome).

3. **Wrap inline `<script>` blocks containing Turion fallback data.** netsuite-project-evms has a 600-line `<script>` with `WBS_DETAIL` / risk register / variance narratives. salesforce-account has a 540-line `<script>` with `SF_CONTACTS_FALLBACK` / `SF_OPPS_FALLBACK` Turion data. arena-bom has a 650-line BOM tree render JS. ns-record has a 1780-line universal record renderer JS. workflow-e2e has a 275-line render JS with `'USSF SSC'` / `'PROJ-ANDROMEDA-SAT-001'` fallbacks. Wrapping each `<script>` element with `<div data-tenant-only="turion">` causes the Plan 09 shim to remove the entire script element from the DOM for non-Turion tenants. The runtime renderers won't run and won't populate any DOM with stale Turion data.

4. **`style="display:contents;"` on arena-main inner wrapper.** `.arena-main` is `display:grid; grid-template-columns: 280px 1fr`. Without `display:contents;`, a regular wrapping `<div>` would become a single grid cell containing both the sidebar AND the main — breaking the layout. `display:contents` makes the wrapper invisible to the grid algorithm while still being targetable by the shim.

5. **Audit block-detector commits separately (a03a163) after first Task 2 page wrap.** The Task 1 commit (257faa1) shipped the wrong-cut block-detector (per-line regex, didn't handle multi-line opening tags). Once the first page's audit showed the bug (67 violations on netsuite-customer-so even with wraps applied), did the deeper fix (multi-line regex + LIFO popping of all wrapper-tag opens). Could have squashed; chose to commit separately so the audit-substrate refinement has its own atomic commit + clear bug-explanation message.

6. **Accept ~12 residual hits on the 9 pages as documented narrative-fallback.** Module-strip nav (`<a href="/projects/evms">Project · EVMS</a>` shown on every NS page for every tenant) is universal nav chrome — not narrative. Arena "★ ITAR Workspace" + SF "FedRAMP-High · ITAR-supported" branding pills are universal Government Cloud marketing — shown to every tenant by design. `z-first-item-id` static fallback "SAT-001" is replaced at runtime by data-loader for every tenant. None of these are actual narrative leaks — the existing tenant-data-driven substitution layers handle them at runtime (per Plan 06 / 07 / 09).

- **Found during:** Task 2, first page (netsuite-customer-so audit after wraps applied)
- **Issue:** First-cut `computeBlockLevelMask()` used per-line regex. When an HTML element's opening tag spans line breaks (e.g. `<div class="ns-form"\n  data-edit-id="...">`), the regex on the first line failed to match (no `>` on the line) and the regex on the second line matched only the attributes (no `<` on the line). As a result, only 1 of 67 hits on netsuite-customer-so was correctly detected as wrapped.
- **Fix:** Switched to single-pass `[\s\S]*?` regex across the whole file (multi-line tag aware). Push ALL wrapper-tag opens onto the stack with `{tag, hasAttr}` entries. Track `attrDepth` and `attrStartLine` so each `[data-tenant-only]` block's covered line range is marked correctly on close. Self-closing tag guard via `/\/\s*$/.test(attrs)`.
