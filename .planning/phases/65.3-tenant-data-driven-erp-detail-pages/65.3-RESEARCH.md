# Phase 65.3: Tenant-data-driven ERP detail pages — Research

**Researched:** 2026-05-17
**Domain:** Multi-tenant data binding for vanilla-HTML ERP demo pages (zero framework, AWS Lambda + RLS Aurora backend)
**Confidence:** HIGH — entire stack is in-repo, pattern already proven by Phases 36 / 62 / 65.2; no library evaluation needed

---

## Summary

The 34 pages in this scope split into 4 ARCHETYPES, each with a different refactor strategy. **Most of the work is mechanical** (replace hardcoded HTML rows with `Object.values(window.X_DATA).map(...).innerHTML`) because Phase 36 already wired `data-loader.js` to populate `window.ITEM_DATA / SO_DATA / NCR_DATA / ...` from `GET /api/data/all` for the CALLING TENANT. The pages still render off those globals when they exist — but most pages additionally have HARDCODED Turion HTML sections that ignore the globals and ship Turion content unconditionally.

The PRIMARY RISK is **NOT the refactor itself** — it's **`TurionDataPreservedCheck`**. Several pages render values that are NOT in any `turion.*` table (e.g. `executive-cockpit.html`'s 8 hardcoded subsidiaries, `architecture.html`'s SAT-001 walkthrough, financial pages' P&L numbers, `mes-shop-floor.html`'s stage detail, FP&A 13-week cashflow, indirect rate true-up). Refactoring those to API will **blank out Turion's view** unless we first seed the missing data into Turion's tenant — but the user has explicitly forbidden touching Turion's existing rows. **Solution: additive Turion seeds (new rows in tables Turion is sparse in), never modifying any existing row.**

The SECONDARY RISK is that ~7 of the 34 pages are not really "tenant data" pages at all — they are PLATFORM/MARKETING content (architecture diagram, demo walkthrough, generic home, admin landing). For those, the right pattern is `data-z-tenant-name`/`data-z-tenant-instance` populators (Phase 63 pattern) + a `live-bind` tenant rollup strip (Phase 62 pattern), NOT a full data-driven render.

**Primary recommendation:** Three-batch refactor (List pages first, Single-record/Create pages second, Dashboard + Special pages third), preceded by an additive Turion data-completeness seed (migration 039), guarded by snapshot-diff (Playwright headless against Turion before + after each batch). 11+11+12 split per ROADMAP is correct but should be re-ordered: dashboards FIRST in their own batch because they already have `/api/dashboards/<role>` coverage from Phase 62 and just need the static text removed.

## Architecture Patterns

### Existing Pattern: List-page refactor recipe (vanilla, ~30 LOC per page)

**Source: Phase 36 + 65.2 pattern, verified in `inventory-index.html` + `manufacturing-index.html`**

Current state (HARDCODED row literal):
```html
<tbody>
  <tr><td>SAT-001</td><td>ADCS-RW-MEDIUM-A</td><td>Reaction Wheel · Medium</td><td>$182,400.00</td></tr>
  <tr><td>SAT-001</td><td>ADCS-RW-008</td><td>Sub-component</td><td>$45,200.00</td></tr>
  <!-- ... 20 more rows ... -->
</tbody>
```

Target state (DATA-DRIVEN):
```html
<tbody id="itemsTable"></tbody>
<script>
window.addEventListener('turion-data-ready', () => {
  const items = Object.values(window.ITEM_DATA || {});
  const tbody = document.getElementById('itemsTable');
  if (items.length === 0) {
    tbody.innerHTML = `<tr><td colspan="4" class="empty-state">
      <strong>No items yet.</strong>
      <a href="/onboarding/migrate" class="cta">Run the import wizard →</a>
    </td></tr>`;
    return;
  }
  tbody.innerHTML = items.map(i => `
    <tr>
      <td>${esc(i.subsystem || '—')}</td>
      <td><a href="/records/item/${esc(i.id)}">${esc(i.id)}</a></td>
      <td>${esc(i.name || i.description || '')}</td>
      <td>${fmtMoney(i.unitCost)}</td>
    </tr>`).join('');
});
function esc(s) { return String(s||'').replace(/[&<>"']/g, c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":"&#39;"}[c])); }
function fmtMoney(n) { return n ? '$' + Number(n).toLocaleString(undefined,{minimumFractionDigits:2,maximumFractionDigits:2}) : '—'; }
</script>
```

**Key points:**
- `window.addEventListener('turion-data-ready', ...)` is the existing signal (data-loader.js emits this; line 131)
- `Object.values(window.ITEM_DATA || {})` works whether ITEM_DATA is populated (Turion / Solo Brands), empty `{}` (new tenant), or `undefined` (fetch failure)
- `esc()` MUST be used on every interpolation — XSS via tenant-controlled item.name
- Empty state in the same render path — no separate component

### Anti-Patterns to Avoid

- **DO NOT introduce a JS framework.** Vanilla pattern is set by 91 sibling pages.
- **DO NOT inline tenant-specific HTML behind feature flags.** The page MUST be tenant-agnostic at the HTML layer; tenant context comes from `erpApi.get()` + `window.X_DATA`.
- **DO NOT delete the existing inline `*-data.js` static files yet** (`enterprise-data.js`, `qms-data.js`, `mes-data.js`, `coa-data.js`, `fpa-data.js`, ...). They are the OFFLINE FALLBACK when `data-loader.js` fails. Data-loader uses them as fallback hydrators if API is unreachable. Removing them breaks the offline-banner pattern from `data-loader.js:147`. Phase 36 RESEARCH explicitly preserved them.
- **DO NOT modify Turion's existing rows in `turion.*` tables.** Migration 039 is ADDITIVE ONLY (`INSERT … ON CONFLICT DO NOTHING`).
- **DO NOT hardcode any Solo Brands token** (ISLE / ORU / CHUB / Solo Stove) in any page. Pages must be tenant-agnostic.
- **DO NOT add per-page authentication overrides.** All pages use the standard `cognitoAuth.requireSession()` → `erpApi` pattern. No custom JWT handling.

## Common Pitfalls

### Pitfall 1: Refactoring a page that Turion has NO data for blanks out Turion's view
**What goes wrong:** User opens dashboard-cto on Turion after refactor → page shows "No NCRs yet" empty state because the API returned `[]` — but Turion HAS NCRs in `turion.ncrs`, the refactor just bound to the wrong key.
**Why it happens:** Inline `*-data.js` files (qms-data.js / mes-data.js / coa-data.js) use slightly different key names than `data-loader.js`. E.g., `NCR_DATA` vs `ncrs` vs `ncr_data`. Refactor binds to one, data-loader populates the other.
**How to avoid:** Pre-flight snapshot of Turion view (TurionDataPreservedCheck) MUST happen BEFORE refactor begins per batch. Snapshot captures rendered DOM text + visible row counts. Post-batch snapshot diffs against pre-batch. ANY semantic loss for Turion = STOP, fix, re-run.
**Warning signs:** Empty state visible on Turion page after refactor.

### Pitfall 2: Snapshot tool can't see hydrated DOM (timing race)
**What goes wrong:** Puppeteer loads page, captures DOM, exits — but `data-loader.js` is still fetching `/api/data/all` (cold start can be 1-2s). Snapshot misses everything.
**Why it happens:** Puppeteer's default `waitUntil: 'load'` fires before XHR completes. `'networkidle2'` fires after 2 XHR-quiet seconds but our keepalives may interfere.
**How to avoid:** Use `page.waitForFunction(() => window.__TURION_DATA_SOURCE__ === 'live-aws')` — data-loader.js:130 sets this AFTER fetch completes. Also `await window.__TURION_DATA_READY__` (line 151 — the promise). Add a 10s timeout + fail-loud on miss.
**Warning signs:** Snapshot has identical content for Turion + Solo Brands (means JS never ran).

### Pitfall 3: Cross-tenant data leak via stale `window.X_DATA`
**What goes wrong:** Snapshot script logs in as Turion, captures Turion view, then re-uses the same Puppeteer browser context for Solo Brands → window.ITEM_DATA still holds Turion items.
**Why it happens:** SPA-style globals persist across page navigations within same browser context. `data-loader.js` only sets globals if API returns non-empty.
**How to avoid:** New browser context per tenant. `browser.createIncognitoBrowserContext()` for each tenant in the matrix. OR fully reload via `page.reload({waitUntil: 'networkidle2'})` after switching `X-Tenant-Slug` (but X-Tenant-Slug comes from hostname, not header — so reload only helps after `page.goto(`https://${slug}.zietra.com/...`)`).
**Warning signs:** Solo Brands snapshot contains SAT-001.

### Pitfall 4: Inline `*-data.js` files override the API
**What goes wrong:** Refactored page calls `window.ITEM_DATA` expecting Solo Brands items, but the page's own inline `<script src="enterprise-data.js"></script>` ran AFTER `data-loader.js` and overwrote with Turion offline data.
**Why it happens:** Script load order matters. `data-loader.js` sets globals conditionally (`if (d.ITEM_DATA && Object.keys(d.ITEM_DATA).length)`), but the static fallback files unconditionally assign.
**How to avoid:** PER PAGE during refactor: either (a) remove the static `<script src="*-data.js">` tags entirely if the API covers everything the page needs, OR (b) move static script tags BEFORE `data-loader.js` so API hydration wins. Recommend (a) for pages whose data is 100% API-covered, (b) for pages that need static fallback (FP&A, BUDGET, FORECAST, TAX_RATES per data-loader.js comment line 145).
**Warning signs:** Solo Brands page shows Turion content (`SAT-001` appears) even after refactor.

### Pitfall 5: XSS via tenant-controlled item names
**What goes wrong:** Solo Brands user creates an item named `<script>alert(1)</script>` → refactored page does `tbody.innerHTML = items.map(i => `<td>${i.name}</td>`)` → XSS.
**Why it happens:** Vanilla string concatenation without escaping.
**How to avoid:** EVERY interpolation goes through `esc(...)`. Add a per-page helper (4-line function in the recipe). Validate the audit script also checks for un-escaped interpolation as a violation.
**Warning signs:** Sensitive — not visible in normal smoke. Add an XSS payload to the synthetic test tenant's items as a smoke check.

### Pitfall 6: New API routes leak data across tenants
**What goes wrong:** New `/api/netsuite/tb` route forgets to use `withTenantClient` → query runs as service role → returns ALL tenants' journal entries.
**Why it happens:** Copy-paste from a non-RLS code path, or forgetting `tenantContext + requireAuth` middleware mount.
**How to avoid:** EVERY new route MUST be added INSIDE the existing `r.use(tenantContext, requireAuth)` block in netsuite.ts (line 9). Every query MUST go through `withTenantClient(req, async (client) => …)`. Tests assert cross-tenant isolation (smoke runs same endpoint with X-Tenant-Slug=turion and X-Tenant-Slug=solobrands → different non-empty arrays).
**Warning signs:** `grep -L withTenantClient backend/src/routes/*.ts` — any file not using it is suspicious.

### Pitfall 7: Cold-start cascade — 34 pages × 3 API calls each
**What goes wrong:** Solo Brands user logs in fresh, clicks through 5 pages quickly → each page hits the Lambda cold (different routes) → 5 × 2s cold start = 10s perceived lag.
**Why it happens:** Lambda cold start + Aurora RDS Proxy hot-pool depletion on burst.
**How to avoid:** (a) Most pages can share `/api/data/all` (already exists, populates 30+ globals in one call); refactored pages that bind to those globals share the call. (b) New aggregator routes (tb, pl, bs) deliberately fetch from already-hot tables.
**Warning signs:** Production-tier Lambda metrics show p99 > 3s after deploy.

### Pitfall 8: Test residue (5th synthetic tenant) leaks into production tenant list
**What goes wrong:** Smoke creates tenant `test65empty`, validates empty states, fails to clean up → tenant remains in `public.tenants` → shows in admin tenant picker → confusing.
**Why it happens:** Smoke harness round-trip skipped or partially failed.
**How to avoid:** Quick 339 pattern — guarded transactional DELETE in smoke's teardown step. Assert tenant_count BEFORE + AFTER identical. Smoke fails if teardown fails.
**Warning signs:** `SELECT slug FROM public.tenants` shows `test65empty` after smoke completes.

### Pitfall 9: Phase-63 `rewriteTitle()` breaks for pages with "Turion" in their tenant name
**What goes wrong:** A future tenant named "Turion Defense" (hypothetical) opens netsuite-tb.html → title is `NetSuite · Trial Balance · Turion Space` → rewriteTitle replaces `Turion Space` → `Turion Defense` (correct) but then the standalone-Turion regex re-fires on the new text.
**Why it happens:** `app-shell.js:430-432` guards against this for `Turion`-named tenants. Already handled.
**How to avoid:** Verify the guard is intact and works for all 34 page titles. Phase 63 already proved this.
**Warning signs:** Title contains "Defense Space" or "Defense Defense" or similar duplication.

### Pitfall 10: SAT-001 hardcoded in MORE places than the audit catches
**What goes wrong:** Audit scans for 8 listed tokens. But `dashboard-cto.html` line 81 hardcodes `/records/project/PROJ-ANDROMEDA-SAT-001` in a Quick Links list. After refactor, that link still exists. Solo Brands user clicks → 404 (no such project).
**Why it happens:** Audit tokens are conservative. Page logic embeds Turion-only resources beyond what we see at first glance.
**How to avoid:** Expand audit token set after each batch's snapshot diff reveals new Turion-only strings. Iterate. Add `Turion`, `aerospace`, `space-grade`, `satellite`, `ITAR`, `DCMA`, `CMMC`, `BCT` to the audit script's token list.
**Warning signs:** Solo Brands user reports broken links.

```javascript
#!/usr/bin/env node
// scripts/audit-hardcoded-erp.mjs · Phase 65.3
// Dependency-free static analyzer. Scans every ERP *.html for Turion-specific
// tokens. Exits 1 on any violation, 0 if clean. Outputs JSON report.
import fs from 'node:fs';
import path from 'node:path';

const TOKENS = [
  'SAT-001', 'ADCS-RW-MEDIUM', 'Blue Canyon', 'PROJ-ANDROMEDA',
  'CLIN-004', 'Honeywell · Aerospace', 'BCT-RW-', 'Cygnus',
  // Phase 65.3 extensions — recommend adding after pre-flight scan
  // 'aerospace-grade', 'space-grade', 'ITAR Cat XV', 'CMMC L2',
];

const ROOT = path.resolve(process.argv[2] || '/Users/jeet/turion-space-demo');
const EXCLUDE = ['/satellite/', '/backend/', '/node_modules/', '/.git/', '/.superpowers/', '/onboarding/'];

const violations = [];
walkDir(ROOT);

function walkDir(dir) {
  for (const entry of fs.readdirSync(dir, { withFileTypes: true })) {
    const full = path.join(dir, entry.name);
    if (EXCLUDE.some(e => full.includes(e))) continue;
    if (entry.isDirectory()) walkDir(full);
    else if (entry.name.endsWith('.html')) scanFile(full);
  }
}

function scanFile(file) {
  const lines = fs.readFileSync(file, 'utf8').split('\n');
  lines.forEach((line, i) => {
    for (const tok of TOKENS) {
      if (line.includes(tok)) violations.push({ file: path.relative(ROOT, file), token: tok, line: i + 1, excerpt: line.trim().slice(0, 120) });
    }
  });
}

const report = { total_files_scanned: 0, violations, by_file: {} };
for (const v of violations) {
  if (!report.by_file[v.file]) report.by_file[v.file] = [];
  report.by_file[v.file].push(v);
}
console.log(JSON.stringify(report, null, 2));
process.exit(violations.length === 0 ? 0 : 1);
```

### Snapshot tool pattern (Puppeteer)

```javascript
#!/usr/bin/env node
// scripts/snapshot-turion-erp-views.mjs · Phase 65.3
import puppeteer from 'puppeteer';

const PAGES = [
  'netsuite-financials', 'netsuite-tb', 'netsuite-bs', 'netsuite-coa',
  'netsuite-arm', 'netsuite-procurement', 'netsuite-items',
  'arena-qms', 'arena-bom', 'dashboard-cto', 'dashboard-cfo',
  'executive-cockpit', 'inventory-index', 'manufacturing-index',
  // … all 34 pages
];

async function snapshotTenant(tenant, idToken) {
  const browser = await puppeteer.launch({ args: ['--no-sandbox'] });
  const out = {};
  for (const page of PAGES) {
    const ctx = await browser.createIncognitoBrowserContext();
    const tab = await ctx.newPage();
    // Inject cognito session into localStorage before navigation
    await tab.evaluateOnNewDocument((tok) => {
      localStorage.setItem('cognito-id-token', tok);
    }, idToken);
    await tab.goto(`https://${tenant}.zietra.com/${page}.html`, { waitUntil: 'networkidle2' });
    // Wait for data-loader.js to resolve (data-loader.js:130 sets this)
    await tab.waitForFunction('window.__TURION_DATA_SOURCE__ === "live-aws"', { timeout: 10000 }).catch(() => {});
    const dom = await tab.evaluate(() => ({
      title: document.title,
      bodyText: document.body.innerText.slice(0, 50000),
      rowCounts: {
        tables: document.querySelectorAll('table tbody tr').length,
        emptyStates: document.querySelectorAll('.empty-state').length,
      },
    }));
    out[page] = dom;
    await ctx.close();
  }
  await browser.close();
  return out;
}

// Run as: node snapshot-turion-erp-views.mjs turion > /tmp/turion-snapshot-before.json
```

### New backend gap-fill route (CoA aggregator)

```typescript
// in backend/src/routes/netsuite.ts — add INSIDE the existing `r.use(tenantContext, requireAuth)` scope

// === Chart of Accounts — derived from gl_accounts (no new table needed) ===
r.get('/coa', async (req, res) => {
  const data = await withTenantClient(req, async (client) => {
    const r = await client.query(
      `SELECT id, source_data FROM turion.gl_accounts ORDER BY id`
    );
    return r.rows.map(row => ({
      account: row.id,
      ...row.source_data,
    }));
  });
  res.json(data);  // empty [] for empty tenants — page handles via empty-state
});

// === Trial Balance — aggregate by gl_account for a period ===
r.get('/tb', async (req, res) => {
  const period = String(req.query.period || '').match(/^\d{4}-\d{2}$/)?.[0];
  if (!period) return res.status(400).json({ error: 'period=YYYY-MM required' });
  const data = await withTenantClient(req, async (client) => {
    const r = await client.query(`
      SELECT
        (source_data->>'gl_account') AS gl_account,
        SUM((source_data->>'debit')::numeric)  AS debit,
        SUM((source_data->>'credit')::numeric) AS credit
      FROM turion.journal_entries
      WHERE source_data->>'period' = $1
      GROUP BY source_data->>'gl_account'
      ORDER BY 1
    `, [period]);
    return { period, lines: r.rows };
  });
  res.json(data);
});
```

```bash
declare -A SB_FORBIDDEN=( [netsuite-items]="SAT-001\|ADCS\|Blue Canyon\|PROJ-ANDROMEDA" )

for page in "${PAGES[@]}"; do
  # Turion content preserved
  curl -sf -b "id_token=$TURION_TOKEN" "$WEB_TURION/$page.html" -o /tmp/$page-t.html
  grep -q "${TURION_TOKENS[$page]:-}" /tmp/$page-t.html && ok "Turion $page contains expected token"

  # Solo Brands shows their data, NO Turion tokens
  curl -sf -b "id_token=$SB_TOKEN" "$WEB_SB/$page.html" -o /tmp/$page-s.html
  grep -q "${SOLOBRANDS_TOKENS[$page]:-}" /tmp/$page-s.html && ok "SB $page contains SB token"
  grep -Eq "${SB_FORBIDDEN[$page]:-NEVERMATCH}" /tmp/$page-s.html && fail "SB $page LEAKS Turion token"

  # Empty tenant shows clean empty state
  curl -sf -b "id_token=$EMPTY_TOKEN" "$WEB_EMPTY/$page.html" -o /tmp/$page-e.html
  grep -q "empty-state\|no items yet\|no data yet\|Run the import wizard" /tmp/$page-e.html && ok "$page empty state"
done

# Round-trip: delete test65empty tenant + assert public.tenants count restored
```

**Note:** curl-based HTML grep is sufficient for SMOKE because the refactored pages will have content rendered in the SHELL (HTML <template>) PLUS dynamic content rendered via JS. The SHELL alone contains the brand text (data-z-tenant-name fallback "Turion Space" → Phase 63 swaps to "Solo Brands" at runtime ONLY in browser, not curl). For the dynamic content assertions, we need Puppeteer — extend the smoke to run Puppeteer for a 5-page sample (the heaviest) and curl for the other 29.
