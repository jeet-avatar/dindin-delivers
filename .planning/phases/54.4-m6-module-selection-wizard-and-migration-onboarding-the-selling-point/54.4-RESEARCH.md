### Pattern 1: Pure Rule Engine (Testable Without DB)

**What:** The rule engine is a pure function `(answers: Answers, catalog: Module[]) => Recommendations`. No I/O. No Postgres. No Cognito. Just a JSON lookup table + sum.

**When to use:** Whenever business logic doesn't need external state, keep it pure. Trivially testable, can run on the client OR server identically, no auth concerns. This is the same pattern as `lib/invite.ts` (pure invite-token generation) from Phase 54.1.

**Example:**

```typescript
// backend/src/onboarding/rule-engine.ts
// PURE — no imports from db/cognito/secrets. Testable in isolation.

import RULES from './recommend-rules.json';

export type Answers = {
  industry: 'aerospace' | 'd2c-ecommerce' | 'saas' | 'manufacturing' | 'distribution' | 'services' | 'other';
  team_size: 'solo' | '2-10' | '11-50' | '51-200' | '201-1000' | '1000+';
  pain_point: 'no-erp' | 'spreadsheet-hell' | 'qb-too-small' | 'compliance-asc606' | 'no-crm' | 'inventory-chaos';
  tools_today: Array<'quickbooks' | 'salesforce' | 'netsuite' | 'excel' | 'sap' | 'none'>;
  asc606_needs: 'yes-now' | 'maybe-2026' | 'no';
};

export type Recommendation = {
  module_code: string;
  score: number;
  reasons: string[];   // each reason cites which question triggered it
};

const ALL_MODULES = [
  'crm','sales','purchase','items','plm','mes','quality',
  'lean-erp-pro','asc606','royalty','dropship','ai-agents','qb-migration',
];

export function recommend(answers: Answers): Recommendation[] {
  const scores = new Map<string, { score: number; reasons: string[] }>();
  for (const m of ALL_MODULES) scores.set(m, { score: 0, reasons: [] });

  // For each answer, look up the contribution per module in RULES JSON.
  for (const [questionKey, answer] of Object.entries(answers)) {
    const answerList = Array.isArray(answer) ? answer : [answer];
    for (const ans of answerList) {
      const contribution = (RULES as any)[questionKey]?.[ans] ?? {};
      for (const [moduleCode, scoreAndReason] of Object.entries<any>(contribution)) {
        const entry = scores.get(moduleCode);
        if (!entry) continue;
        entry.score += scoreAndReason.score;
        if (scoreAndReason.reason) entry.reasons.push(scoreAndReason.reason);
      }
    }
  }

  // Convert + sort by score desc, slice top 3-7, threshold: include if score >= 3.
  return [...scores.entries()]
    .map(([code, v]) => ({ module_code: code, score: v.score, reasons: v.reasons }))
    .filter(r => r.score >= 3)
    .sort((a, b) => b.score - a.score)
    .slice(0, 7);
}
```

### Pattern 2: Cross-Tenant Read with RLS-Enforced Write (Sample-Data Clone)

**What:** Clone Turion's `turion.*` schema rows (source `tenant_id=00000000-0000-0000-0000-000000000001`) into a brand-new tenant. SELECT must bypass RLS (cross-tenant read); INSERT must go through `withTenantClient` so RLS is enforced (target tenant_id is rewritten, GUC is set).

**When to use:** Any time we read from one tenant and write to another for legitimate operational reasons (demo data clone, support-tenant impersonation, etc.).

**Example:**

```typescript
// backend/src/onboarding/sample-data-clone.ts
// SAFETY: bypass role for SELECT (cross-tenant read), withTenantClient for INSERT (RLS-enforced).
import { Pool } from 'pg';
import { withTenantClient } from '../db';
import type { Request } from 'express';

// Bypass pool is a separate pg.Pool wired with `zietra_admin_bypass` credentials
// from `dollor/production/database-url-bypass-…` secret. Provisioned in Phase 55-02.
import { bypassPool } from '../db-bypass';

const TURION_TENANT_ID = '00000000-0000-0000-0000-000000000001';

// Tables to clone (allowlist — DO NOT clone audit_log, api_keys, *_secrets).
const CLONE_TABLES = [
  'turion.sf_accounts', 'turion.sf_contacts', 'turion.sf_opportunities',
  'turion.ns_customers', 'turion.ns_items', 'turion.ns_vendors',
  'turion.ns_journal_entries', 'turion.arena_parts', 'turion.arena_ecos',
  'turion.mes_work_orders', 'turion.mes_build_steps',
];

// Tables NEVER cloned (security or correctness reasons).
const BLOCKLIST = new Set([
  'audit_log',
  'tenant_users',          // every tenant has their own admins
  'tenant_features',       // wizard already set these
  'api_keys', 'secrets',   // tenant-specific credentials
]);

export async function cloneSampleData(
  req: Request,
  options: { skipTables?: string[] } = {},
): Promise<{ rowsByTable: Record<string, number>; totalRows: number }> {
  const skip = new Set(options.skipTables ?? []);
  const tablesToClone = CLONE_TABLES.filter(
    t => !skip.has(t) && !BLOCKLIST.has(t.split('.')[1]),
  );

  const result: Record<string, number> = {};
  let total = 0;

  for (const tableName of tablesToClone) {
    // 1. SELECT via bypass pool — cross-tenant read of Turion's rows.
    const sourceRows = await bypassPool.query(
      `SELECT * FROM ${tableName} WHERE tenant_id = $1`,
      [TURION_TENANT_ID],
    );

    // 2. INSERT via withTenantClient — RLS sets app.tenant_id to req.tenant.id.
    //    Postgres' RLS policy will verify every row's tenant_id matches.
    //    We REWRITE tenant_id + regenerate any UUID PKs to avoid collisions.
    await withTenantClient(req, async (client) => {
      for (const row of sourceRows.rows) {
        const cleaned = { ...row };
        cleaned.tenant_id = req.tenant!.id;     // Rewrite to target tenant.
        if (cleaned.id && typeof cleaned.id === 'string') {
          // Regenerate UUID PKs — would otherwise collide if the source has
          // hard-coded UUIDs (Turion's seed data does).
          cleaned.id = crypto.randomUUID();
        }
        const cols = Object.keys(cleaned);
        const vals = cols.map(c => cleaned[c]);
        const placeholders = cols.map((_, i) => `$${i + 1}`).join(', ');
        await client.query(
          `INSERT INTO ${tableName} (${cols.join(', ')}) VALUES (${placeholders})`,
          vals,
        );
      }
    });

    result[tableName] = sourceRows.rows.length;
    total += sourceRows.rows.length;
  }

  return { rowsByTable: result, totalRows: total };
}
```

**Security note:** The bypass pool only does SELECT. INSERT goes through the standard tenant-context pool with RLS active. If a future bug attempts to write with the bypass role, RLS won't catch it — but the code path doesn't even import a bypass-write client, so the bug can't happen by accident.

### Anti-Patterns to Avoid

- **Anti-pattern: Hand-rolled CSV parser.** Salesforce exports embed commas + newlines + escaped quotes inside `Description` fields. `papaparse` handles RFC 4180 + dialects correctly; a `split(',')` will misalign columns silently and corrupt the import.
- **Anti-pattern: Bypass-role INSERT.** Never write through `bypassPool`. The role exists for SELECT-only cross-tenant reads (sample-data clone, support tools). RLS won't protect you if you bypass.
- **Anti-pattern: Server-driven SSE for the wizard.** The wizard is a single-page interaction, no async. Keep it as a normal POST→200 round trip with a spinner.
- **Anti-pattern: Storing the wizard answers long-term.** We store the **result** (`onboarding_state` JSONB + `tenant_features` rows), not the raw answers. If the user wants to re-run, they re-take the wizard. (Optional: stash the last-completed answers in `onboarding_state.last_wizard_answers` for "show me what I picked last time" — at the planner's discretion.)
- **Anti-pattern: Modal-only wizard.** Use a dedicated page (`/onboarding/recommend`) — direct-linkable from email campaigns, bookmarkable, single back-button = back to catalog. Modal trapping in `/catalog` is hostile to deep links.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CSV parsing with quoted fields, commas-in-cells, newlines-in-cells | `String.split(',')` | `papaparse@5.x` (CDN or npm) | Salesforce Description/Notes routinely contain `,` and `\n`. Split-based parsing silently corrupts columns. papaparse is RFC 4180 + Excel-dialect compliant. |
| Tenant-scoped DB writes | `pool.query(...)` directly + manual `WHERE tenant_id = ?` | `withTenantClient(req, fn)` | Phase 55 RLS enforces this at the DB layer. Direct `pool.query` against RLS-enabled tables 403s without `SET app.tenant_id` GUC. Pattern proven across 96 routes already. |
| Role-based authorization | `if (req.role === 'admin')` in handler | `requireRole('admin')` middleware | Phase 54.1 pattern; reads from `tenant_users` (DB), not JWT (which can be stale); has 60s cache; centralizes audit logging. |
| Cognito session validation | manual JWT verify with hardcoded JWKS | `requireAuth` middleware | Phase 38 pattern; verifies ES256 against JWKS fetched from Secrets Manager at cold start; centralized hardened error shape. |
| CloudFront clean-URL routing | Static URL list scattered across HTML | `cf-function-source/turion-clean-urls.js` central map | Single source-of-truth for 80+ pretty URLs; deployed once, the catalog/team/onboarding pages can all link to clean URLs with no per-page JS. |
| Idempotent migration SQL | Hand-written `BEGIN; ... COMMIT;` blocks per call | Migration file in `backend/migrations/032_*.sql` applied via Phase 55 one-shot Lambda `zietra-rls-runner-55-05` | Phase 55-05 Lambda is already provisioned; pass `{password, user, host, sql}` payload; returns parsed result. |
| Onboarding state persistence | Separate table with FK + indexes + audit columns | JSONB column `tenants.onboarding_state` | Single-row update, no migration drift over time, easy to add new checklist items (just add a JSON key). Pattern used for `disclosures.json`, `setup-data.js`, etc. across the codebase. |
| Sample-data clone | Custom dump/restore | SELECT + transformed INSERT through `withTenantClient` | pg_dump requires DB-admin creds in the Lambda; SELECT/INSERT through pg's regular Pool works in-band, keeps RLS active for the writes, doesn't require extra IAM. |

**Key insight:** Phase 54.4 is **plumbing on top of finished primitives**. Every hard problem (auth, tenant resolution, role gating, RLS, migration tooling) was solved by Phases 41 / 50 / 53 / 54.1 / 55. The remaining work is: 6 HTML pages + 1 route file + 1 JSON file + 1 migration. The temptation to "improve" the underlying pattern (e.g., refactor `withTenantClient`, add a new auth path) should be resisted — those changes break 200+ existing routes.

## Common Pitfalls

### Pitfall 1: `X-Tenant-Slug` Header Missing on First-Time Anonymous Visits

**What goes wrong:** A new user clicks the signup magic link, lands on `/onboarding/recommend` via redirect, but the CloudFront Function only sets `X-Tenant-Slug` when the host is `<slug>.zietra.com`. If they're on `zietra.com/onboarding/...` (apex), the header is absent → backend returns 400 "Missing X-Tenant-Slug header".

**Why it happens:** The CF Function logic checks `host.endsWith('.zietra.com')` AND extracts the prefix — apex `zietra.com` doesn't match this pattern.

**How to avoid:** The signup flow lands the user at `https://<their-slug>.zietra.com/cognito-auth-callback?...` (Phase 41 pattern); the callback redirects to `/onboarding/recommend` ON THE TENANT SUBDOMAIN. **Verify the redirect target uses the tenant subdomain, not apex.** Cross-check `signup.html:107` (`localStorage.setItem('zietra-cognito-erp-redirect', '/')`) — should remain `/` so post-auth lands on tenant home; tenant home reads `onboarding_state` and redirects to `/onboarding/recommend` if incomplete.

**Warning signs:** Backend logs show `[tenantContext] DB lookup failed: Missing X-Tenant-Slug header` from a freshly-signed-up user.

### Pitfall 2: Migration 032 + RLS

**What goes wrong:** `ALTER TABLE public.tenants ADD COLUMN onboarding_state JSONB` succeeds, but `UPDATE public.tenants SET onboarding_state = ... WHERE id = $1` fails with `permission denied for table tenants` because the wizard runs under the regular `zietra_app` role and the RLS policy on `public.tenants` only allows `SELECT` to non-bypass roles (per migration 030).

**Why it happens:** Phase 55 RLS policy on `public.tenants` is **read-only for app role** (since tenants are created by `/signup` using the master role + direct pool.query). UPDATE was never tested because no app-level UPDATE existed.

**How to avoid:** In migration 032, **also amend the RLS policy** to allow UPDATE-with-row-match (`USING (id = current_setting('app.tenant_id')::uuid)`). Test path: a Turion-tenant request can UPDATE its own tenants row but NOT another tenant's. Add an isolation test to `tests/rls/` mirroring the Phase 55-04 pattern.

```sql
-- migrations/032_onboarding_state.sql (excerpt)
ALTER TABLE public.tenants ADD COLUMN IF NOT EXISTS onboarding_state JSONB
  NOT NULL DEFAULT '{
    "checklist": {"modules": false, "team": false, "data": false, "agents": false},
    "wizard_completed_at": null,
    "last_wizard_answers": null
  }'::jsonb;

-- Allow tenant admins to UPDATE their own row's onboarding_state.
DROP POLICY IF EXISTS tenants_update_own_onboarding ON public.tenants;
CREATE POLICY tenants_update_own_onboarding ON public.tenants
  FOR UPDATE TO zietra_app
  USING  (id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (id = current_setting('app.tenant_id', true)::uuid);
```

**Warning signs:** `permission denied for table tenants` in Lambda logs on PATCH /api/onboarding/checklist.

### Pitfall 3: papaparse Loaded From CDN Inside CSP-Restricted Page

**What goes wrong:** Some browser security settings or future CSP additions block `<script src="https://cdn.jsdelivr.net/...">`. Wizard fails silently when papaparse is `undefined`.

**Why it happens:** No CSP today, but operator-driven security hardening (Phase 54.6 added security headers; future phases will add CSP).

**How to avoid:** Either (a) bundle papaparse into a single `frontend/lib/papaparse-5.4.1.min.js` file checked into the repo and synced to S3 (3 KB extra in the bundle), or (b) defer to CDN with a defensive `if (typeof Papa === 'undefined') { showError('CSV library failed to load — refresh') }` fallback. Recommend (a) for production-grade reliability.

**Warning signs:** `ReferenceError: Papa is not defined` in browser console; users report "Parse button does nothing."

### Pitfall 4: SF CSV Has Variable Column Set Across Orgs

**What goes wrong:** Salesforce Accounts.csv columns vary per org config — `Industry`, `AnnualRevenue`, `Description`, `Phone`, etc. are optional. User exports from a custom-field-rich org; our import expects fields that aren't there.

**Why it happens:** SF Reports → Export builds CSV from a chosen report, not a fixed schema. Custom field labels (`Industry__c`) also vary.

**How to avoid:** Build a **column-mapping step**. After papaparse extracts headers, show a 2-column table: "Your CSV column" ↔ "CRM target field (dropdown)". Pre-fill best-guess matches by exact-string match on common labels (`Account Name` → `name`, `Industry` → `industry`, `Annual Revenue` → `annual_revenue`). User confirms before import. Only require `name` to be mapped; everything else optional. Mirror Phase 37 `FIELD_MAPS` structure (see `backend/src/routes/quickbooks.ts:41`).

**Warning signs:** Imported rows have `NULL` in every column except `name`; users report "where did my data go?"

### Pitfall 5: Sample-Data Clone Hits FK Constraint on PK Regeneration

**What goes wrong:** Sample-data clone regenerates UUIDs for PKs to avoid collisions. But child tables FK back to those PKs — if you regenerate `arena_parts.id` but not `arena_bom_lines.part_id` to match, every BOM line is broken.

**Why it happens:** Naive row-by-row clone doesn't track the PK remap.

**How to avoid:** Build a **PK remap dictionary** during the clone. As you regenerate each PK, store `{old_id → new_id}`. When inserting child tables, look up FK columns in the remap and substitute. Approach:

```typescript
const remap: Record<string, Map<string, string>> = {
  'turion.arena_parts': new Map(),
  'turion.ns_customers': new Map(),
  // ... etc per table
};

for (const tableName of CLONE_TABLES_IN_DEPENDENCY_ORDER) {
  for (const row of sourceRows.rows) {
    const oldId = row.id;
    const newId = crypto.randomUUID();
    remap[tableName].set(oldId, newId);
    row.id = newId;
    row.tenant_id = req.tenant!.id;
    // Rewrite any FK columns by looking up parent-table remap.
    if (row.part_id && remap['turion.arena_parts'].has(row.part_id)) {
      row.part_id = remap['turion.arena_parts'].get(row.part_id);
    }
    // ... etc per FK
    await client.query(`INSERT INTO ${tableName} (${cols.join(', ')}) VALUES (${placeholders})`, vals);
  }
}
```

**Order matters:** parents before children. For Turion data: `parts` before `bom_lines`, `customers` before `sales_orders`, etc.

**Warning signs:** Sample-data clone "succeeds" but BOM page shows empty; or FK violations like `insert or update on table "arena_bom_lines" violates foreign key constraint "arena_bom_lines_part_id_fkey"`.

### Pitfall 6: WAF Blocks Anon CSV Upload as "Suspicious"

**What goes wrong:** A 5K-row Salesforce CSV pasted into a textarea is ~2MB POST body. WAF managed rules (Common Rule Set has a `SizeRestrictions_BODY` rule with 8KB default) may flag and block it.

**Why it happens:** AWS Managed Rules → AWSManagedRulesCommonRuleSet → SizeRestrictions_BODY default = 8192 bytes.

**How to avoid:** (a) Override the SizeRestrictions_BODY rule for `/api/onboarding/migrate/*` paths to allow up to 6MB (Lambda sync limit). (b) **Recommended for v1:** chunk client-side — parse, split into batches of 100 rows, send sequential POSTs of `{batch_num: N, rows: [...]}`. Each POST stays well under 8KB.

**Warning signs:** Browser console shows `403 Forbidden` from CloudFront with `x-amzn-WAFv2-…` headers on `/api/onboarding/migrate/salesforce`. Smaller test files (10 rows) work fine.

### Pitfall 7: Race Condition Between Wizard Finalize and Tenant Self-View

**What goes wrong:** Wizard POSTs `/api/onboarding/finalize` → 200 → frontend redirects to `/` → frontend calls `GET /api/tenants/current` for nav rendering → returns stale `features` list because of the 60s `tenantContext` cache, OR because the wizard's UPDATE hadn't fully committed before the SELECT.

**Why it happens:** Phase 53 `tenantContext` has a 60s positive cache. After the wizard mutates `tenant_features`, the cache still holds the pre-wizard view.

**How to avoid:** The cache holds **tenant identity** (id, slug, name, plan, trial_ends_at) NOT the features list. Features are queried separately in `GET /api/tenants/current` via `withTenantClient`. So the cache is fine. BUT: ensure the wizard's POST awaits the full transaction commit before returning 200. The `withTenantClient` helper auto-commits on success — verify in tests.

**Warning signs:** Users report "I unselected MES but it still shows in my nav." Hard refresh fixes it. → either the tenant cache is too aggressive (unlikely — features bypass the cache) OR the frontend is reading cached `__ZIETRA_TENANT` from `app-shell.js` boot. Force a re-fetch after finalize.

```typescript
// backend/src/routes/onboarding.ts — Phase 54.4 (all 3 plans contribute)
import { Router, Request, Response } from 'express';
import { withTenantClient } from '../db';
import { requireAuth } from '../middleware/auth';
import { requireRole } from '../middleware/role';
import { tenantContext } from '../middleware/tenant';
import { recommend, type Answers } from '../onboarding/rule-engine';
import { cloneSampleData } from '../onboarding/sample-data-clone';

const r = Router();

// All routes require tenantContext + requireAuth.
// Mutating routes additionally require admin role.
r.use(tenantContext, requireAuth);

// === 54.4-01: GET the rules JSON for client-side preview (read-only). ===
r.get('/rules', (_req, res) => {
  const RULES = require('../onboarding/recommend-rules.json');
  res.json(RULES);
});

// === 54.4-01: POST answers → recommendations. ===
// No write — pure compute. Any authenticated tenant user can call.
r.post('/recommend', async (req: Request, res: Response) => {
  const answers = req.body as Answers;
  if (!answers?.industry || !answers?.team_size) {
    return res.status(400).json({ error: 'industry + team_size required' });
  }
  const recommendations = recommend(answers);
  return res.json({ recommendations, total_recommended: recommendations.length });
});

// === 54.4-01: POST finalize → write tenant_features + onboarding_state. ===
// Admin-only — only the tenant owner can change features.
r.post('/finalize', requireRole('admin'), async (req: Request, res: Response) => {
  const selected: string[] = Array.isArray(req.body?.selected_modules) ? req.body.selected_modules : [];
  if (selected.length < 1 || selected.length > 13) {
    return res.status(400).json({ error: 'Select between 1 and 13 modules' });
  }
  // Defensive: validate every module_code against the CHECK constraint set.
  const VALID_CODES = new Set([
    'crm','sales','purchase','items','plm','mes','quality',
    'lean-erp-pro','asc606','royalty','dropship','ai-agents','qb-migration',
  ]);
  if (!selected.every(c => VALID_CODES.has(c))) {
    return res.status(400).json({ error: 'Unknown module code in selection' });
  }
  try {
    await withTenantClient(req, async (client) => {
      // Set all modules' enabled=false, then re-enable the selected ones.
      // Single transaction ensures atomicity.
      await client.query(
        `UPDATE public.tenant_features SET enabled = false
            WHERE tenant_id = $1`,
        [req.tenant!.id],
      );
      for (const code of selected) {
        await client.query(
          `UPDATE public.tenant_features SET enabled = true
              WHERE tenant_id = $1 AND module_code = $2`,
          [req.tenant!.id, code],
        );
      }
      // Mark wizard complete in onboarding_state JSONB.
      await client.query(
        `UPDATE public.tenants
            SET onboarding_state = jsonb_set(
              jsonb_set(onboarding_state, '{checklist,modules}', 'true'::jsonb),
              '{wizard_completed_at}', to_jsonb(now()::text)
            )
          WHERE id = $1`,
        [req.tenant!.id],
      );
    });
    return res.json({ ok: true, redirect: '/' });
  } catch (e: any) {
    console.error('[POST /api/onboarding/finalize] DB error:', e?.message);
    return res.status(500).json({ error: 'Finalize failed' });
  }
});

// === 54.4-03: PATCH checklist item by name. ===
r.patch('/checklist', requireRole('admin', 'manager'), async (req: Request, res: Response) => {
  const item = String(req.body?.item || '');
  const completed = req.body?.completed === true;
  const VALID_ITEMS = new Set(['modules', 'team', 'data', 'agents']);
  if (!VALID_ITEMS.has(item)) return res.status(400).json({ error: 'Unknown checklist item' });
  try {
    await withTenantClient(req, async (client) => {
      await client.query(
        `UPDATE public.tenants
            SET onboarding_state = jsonb_set(
              onboarding_state,
              ARRAY['checklist', $1],
              $2::jsonb
            )
          WHERE id = $3`,
        [item, JSON.stringify(completed), req.tenant!.id],
      );
    });
    return res.json({ ok: true });
  } catch (e: any) {
    console.error('[PATCH /api/onboarding/checklist] DB error:', e?.message);
    return res.status(500).json({ error: 'Checklist update failed' });
  }
});

// === 54.4-02: POST sample-data clone. Admin-only — destructive on this tenant. ===
r.post('/migrate/sample-data', requireRole('admin'), async (req: Request, res: Response) => {
  try {
    const result = await cloneSampleData(req);
    // Mark checklist data step complete.
    await withTenantClient(req, async (client) => {
      await client.query(
        `UPDATE public.tenants SET onboarding_state = jsonb_set(
            onboarding_state, '{checklist,data}', 'true'::jsonb) WHERE id = $1`,
        [req.tenant!.id],
      );
    });
    return res.json({ ok: true, summary: result });
  } catch (e: any) {
    console.error('[POST /api/onboarding/migrate/sample-data] error:', e?.message);
    return res.status(500).json({ error: 'Sample data clone failed' });
  }
});

// (Plus migrate/salesforce, migrate/items, migrate/vendors, migrate/customers — see §E)

export default r;
```

async function parseCSVAndPreview(csvText) {
  const result = Papa.parse(csvText.trim(), {
    header: true,           // Auto-detect first row as headers

    return null;
  }
  const headers = result.meta.fields;
  // Best-guess auto-map.
  const TARGET_FIELDS = [
    { key: 'name',           label: 'Customer name',  required: true },
    { key: 'email',          label: 'Email',          required: false },
    { key: 'phone',          label: 'Phone',          required: false },
    { key: 'industry',       label: 'Industry',       required: false },
    { key: 'annual_revenue', label: 'Annual revenue', required: false },
    { key: 'description',    label: 'Description',    required: false },
  ];
  const autoMap = {};
  for (const t of TARGET_FIELDS) {
    autoMap[t.key] = headers.find(h => h.toLowerCase().includes(t.key.replace('_', ' '))) || '';
  }

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Multi-step form wizards as monoliths (single `<form>` with all questions visible) | Conversational single-question-at-a-time wizards (Typeform-style) OR progressive single-page-all-shown (Stripe Atlas-style) | Mid-2020s SaaS onboarding consensus | Stripe Atlas + Vercel onboarding + Linear setup all use progressive single-page. **Recommend** Stripe Atlas style for 54.4 — all 5 questions visible, submit at end. Easier to skim, easier to back-edit, no animation engineering. |
| Pendo/Userpilot-style overlay tour | In-product checklist tile that stays visible until dismissed | 2023+ | Patterns from Linear, Notion, Stripe Dashboard. Recommend the persistent-tile pattern — overlay tours are universally hated; tile is opt-in scannable. |
| Salesforce Bulk API for SF→CRM import | CSV export + paste → client-side parse + server batch INSERT | N/A (we never had API access) | No OAuth gymnastics; user retains visible audit trail (the CSV file on their disk). Trade-off: missing Salesforce custom fields. Mitigation: column-mapping step. |
| Stored procedure or stored function for tenant data clone | Application-level SELECT (bypass) + INSERT (RLS-enforced) loop with PK remap | Phase 55 RLS pattern (2026-05) | Stored procedures bypass RLS unless `SECURITY INVOKER` is set. App-level keeps RLS in the loop for every INSERT — safer. |
| Hand-rolled CSV parsers in JS | `papaparse` library | papaparse 5.x stable since 2022 | Widely used, RFC 4180 compliant, handles dialect detection. Don't reinvent. |
| Modal-based onboarding ("welcome modal with 3 steps") | Page-based onboarding at deep-linkable URLs (`/onboarding/recommend`) | Mid-2020s consensus | Better SEO, better email-linking (signup confirmation email can deep-link to `/onboarding/recommend`), better back-button behavior. |

**Deprecated/outdated:**
- Server-side CSV parsing for small files — adds Lambda payload limits + complexity vs client-side parse.
- Multipart upload for CSV — text-paste is faster for users and avoids 6MB Lambda sync limit at small scale.
- Per-question backend round-trip — pure rule engine runs client-side just as well (we expose it via `GET /api/onboarding/rules`).

**Reference articles (for the planner during discuss-phase):**

- Stripe Atlas onboarding (single-page progressive disclosure): the canonical "5 questions → here's your set up" UX. Reverse-engineerable at `https://stripe.com/atlas`.
- Pendo "Why product tours are dead": industry consensus that overlay tours have ~40% abandonment rates vs <10% for inline checklists.
- AWS DMS (not used here — overkill): documented because some prospects ask "do you use DMS?" Answer: no, our migration is paste-CSV + cross-tenant clone; DMS is for ongoing CDC replication between two production systems, not one-time onboarding imports.

## Open Questions

1. **Wizard JSON: backend-served via GET vs frontend-checked-in?**
   - What we know: backend-served means tunable post-deploy via Lambda env-var or DB row; frontend-checked-in means a frontend deploy per tweak.
   - What's unclear: how often we'll tune the matrix in practice.
   - Recommendation: backend `GET /api/onboarding/rules` returning the JSON. Reasoning: every modification logs in git via the migration that updates the file, but live A/B tweaks don't require a CloudFront invalidation. The frontend caches the JSON for the session (one fetch on wizard load).

2. **`/onboarding/migrate/customers` vs share `/onboarding/migrate/vendors` template?**
   - What we know: both are tabular CSV imports with similar schemas (name, email, address).
   - What's unclear: whether to ship 1 generic page or 2 dedicated.
   - Recommendation: 1 generic page parameterized by `?type=customers|vendors`. Saves ~150 lines of duplicated HTML. Mirrors how `/sales/new-quote` and `/sales/new-order` share NetSuite chrome.

3. **Sample-data clone: which tables to clone vs skip?**
   - What we know: ~25 tables in `turion.*` schema; some are sensitive (api_keys, audit_log).
   - What's unclear: whether to clone work orders mid-execution (in-progress builds) — semantically weird for a new tenant to inherit an in-progress work order.
   - Recommendation: clone definition tables (parts, items, customers, vendors, agreements) + completed work orders; SKIP in-progress work orders (where `status NOT IN ('completed', 'cancelled')`). Defer the final allowlist to the planner.

4. **WAF SizeRestrictions for `/api/onboarding/migrate/*`?**
   - What we know: AWS managed rules default is 8KB; CSV rows of 5K accounts = ~2MB.
   - What's unclear: whether to override or chunk client-side.
   - Recommendation: chunk client-side at 100 rows per POST. No WAF override needed. Each POST is well under 8KB. Server-side accumulates batches in the same transaction.

5. **Onboarding state visibility: keep checklist forever or auto-hide once complete?**
   - What we know: ROADMAP says "Checklist persists until all checked."
   - What's unclear: post-completion behavior — collapse to badge? Disappear? Move to settings?
   - Recommendation: once all 4 items true, fade out + display a single "Setup complete ✓" badge in the page corner for 24h, then disappear. State remains in DB for analytics.

6. **Migration progress feedback: spinner vs progress bar vs SSE?**
   - What we know: small CSVs (<2K rows) complete in <1s; sample-data clone of full Turion data is ~3-5s.
   - What's unclear: whether to invest in real-time progress.
   - Recommendation: spinner + "this can take up to 10 seconds" copy for v1. SSE in M8 if user complaints surface.
