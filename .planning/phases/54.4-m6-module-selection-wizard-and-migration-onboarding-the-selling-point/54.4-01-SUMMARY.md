## Decisions Made

See key-decisions in frontmatter. Highlights:

1. **Fallback threshold for low-signal answers** — Rule-engine default threshold is `score >= 3` capped at top 7. If fewer than 3 modules score >= 3, threshold drops to `>= 2`. Guarantees every wizard run returns a meaningful (or at least non-empty) result set.
2. **Single-set canonical module-code source** — `ALL_MODULES` const in `rule-engine.ts` is the runtime source-of-truth for module-code validation in `routes/onboarding.ts`. The validation `Set` is built directly from `ALL_MODULES`, so there's no duplicate string array to drift. The vitest "all module codes in result are from the canonical 13-code list" cross-checks the wiring.
3. **Migration 032 as policy addition, not replacement** — Phase 55 RLS on `public.tenants` was SELECT-only for `zietra_app`. Migration 032 ADDs (not replaces) a separate policy `tenants_update_own_onboarding` that gates UPDATE on `id = current_setting('app.tenant_id')::uuid`. The Phase 55 SELECT policy is untouched.
4. **Shared frontend catalog via `/lib/module-catalog.js`** — Extracted from `catalog.html`'s inline array (which is now removed per Rule 5). Both `catalog.html` and `onboarding/recommend.html` load it as `window.MODULE_CATALOG`. Adding a new module is a one-place edit.
5. **`/finalize` uses chained `jsonb_set`** — Single SQL statement updates `onboarding_state.checklist.modules=true` and `onboarding_state.wizard_completed_at=now()` together. Combined with the tenant_features re-toggle, the whole finalize is one `withTenantClient` transaction (atomic, RLS-enforced).

- **Fix:** Switched to `--payload fileb://...json` (raw bytes file mode) which CLI v1 accepts. Same pattern that Phase 55-05 SUMMARY documents as the v1-compatible workaround.
- **Files modified:** none (operator-side).
- **Verification:** Subsequent invokes returned StatusCode 200 with successful JSON results.
