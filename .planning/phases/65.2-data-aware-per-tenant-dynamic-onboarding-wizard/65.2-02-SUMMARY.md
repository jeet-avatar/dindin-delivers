## Decisions Made

1. **Cap widened 7 → 10 (Rule 3 auto-fix).** Plan must_haves truth #4 explicitly requires "exactly Quick-338-9 PLUS asc606 = 10 modules". With the cap at 7, `ai-agents`, `mes`, `quality` (all scoring ≥3) were getting trimmed. The Task 2 action block said "Do NOT change the cap" but the must_haves truth was incompatible with that — must_haves wins. Updated the cap test from "caps at 7" → "caps at 10". Legacy callers without `data_signals` typically produce ≤7 modules at threshold≥3 so the cap bump is functionally a no-op for them (regression check: legacy `{industry:'aerospace', team_size:'201-1000', pain_point:'compliance-asc606', tools_today:['netsuite'], asc606_needs:'yes-now'}` still produces 7 modules — unchanged).

2. **TS union widening for Industry (W4 LOCKED) is cosmetic.** The rule engine reads `recommend-rules.json` not the TS type, so the new industry codes work purely from JSON. The TS union widening is for caller ergonomics (so `Answers` type-checks when set to `'d2c-multibrand'`).

3. **Object.entries type narrowing.** Initial implementation had the runtime `continue` guard for `data_signals` but the TS compiler still complained because it couldn't narrow `answer` after the guard. Solved by casting at the iterator: `Object.entries(answers as Record<string, unknown>)` + explicit `: string[]` on `answerList`. This is the minimum-diff fix; cleaner alternative would be to extract `data_signals` before the loop, but that's a bigger refactor.

4. **Negative scoring (-3 dropship dampener).** The scorer simply sums contributions, so negative scores are valid and well-behaved. Using a -3 on `dropship` for `has_corporate_facts` was the cleanest way to express "corporate D2C operators with employees ≥100 don't typically run drop-ship". Documented in the JSON reason string.

5. **In-memory cache (not DB).** Per W5 / Plan 01 design — `SIGNAL_CACHE: Map<string, CacheEntry>` at module scope. Survives Lambda warm reuse, lost on cold start, no DDL. Cold-start cost of 6 queries ~<100ms is acceptable per research Pitfall 3.

6. **PATCH audit row in same txn.** `auditLog` is called INSIDE the `withTenantClient(req, async (client) => {...})` callback so if either the UPDATE or the audit INSERT fails, both roll back. No orphan audit entries.

### Rule 3 auto-fix: TS type narrowing for the answer loop

- **Found during:** Task 2 `npm run build`.
- **Issue:** Adding `data_signals?: DataSignals` to `Answers` widened the value type in `Object.entries(answers)`. The runtime `continue` guard wasn't sufficient — TS still tried to type-check `questionRules[ans]` with `DataSignals` as a possible index type, giving 4 errors (TS2538, TS18046 × 3).
- **Fix:** `Object.entries(answers as Record<string, unknown>)` + explicit `: string[]` on `answerList` + `(answer as string[])` / `(answer as string)` casts at the array branch. Minimal-diff fix to the existing loop.
- **Files modified:** `backend/src/onboarding/rule-engine.ts`
