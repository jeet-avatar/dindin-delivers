## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Body cap of 500 chars broke python3 JSON parsing**
- **Found during:** Task 4 first smoke run (8 FAILs).
- **Issue:** Original Quick-338 `api_call` helper had `_BODY=$(head -c 500 "$out")`. The new `/profile` response body is ~2272 bytes; `/recommend` response is ~1500+ bytes. python3 received truncated JSON and raised `JSONDecodeError`, cascading into 5+ shape-check FAILs. The truncated body was then echoed in the failure message, making the failures LOOK like API problems when they were actually parse problems.
- **Fix:** Bumped to `head -c 10000` in BOTH `api_call` (original) and `api_call_tenant` (new) helpers. Added comment explaining the rationale.
- **Files modified:** `scripts/smoke-onboarding.sh`
- **Commit:** `b4224df`

**2. [Rule 3 - Blocking] source-reset runner Lambda call silently failed due to missing app.tenant_id**
- **Found during:** Task 4 second smoke run (1 remaining FAIL on round-trip — BEFORE=AFTER but source=user not seeded).
- **Issue:** Step 5's `UPDATE public.tenant_onboarding_profile SET source='seeded' WHERE tenant_id='…'` ran via `zietra_app` role. zietra_app is RLS-gated by `current_setting('app.tenant_id', true)::uuid`. When app.tenant_id is unset, the cast `''::uuid` errors silently and the UPDATE applies 0 rows. The smoke's `ok` was unconditional (didn't check the runner output).
- **Fix:** Prepend `SET app.tenant_id = '$SB_TENANT_ID';` to the SQL (single payload, runner Lambda already replays session settings per invocation per Phase 65-01 pattern). Added explicit `RESET_OK=$(python3 -c "...")` check on the runner Lambda's output to assert `ok:true` BEFORE printing the success message.
- **Files modified:** `scripts/smoke-onboarding.sh`
- **Commit:** `b4224df`

**3. [Rule 3 - Blocking] CHECK A's hard `item_count == 109` failed because Solo Brands data has drifted UP from prior smoke runs**
- **Found during:** Task 4 third smoke run.
- **Issue:** Quick-338 + prior 65.2 smoke runs added `SMOKE-338-*` rows to `turion.items` / `vendors` / `customers` / `sales_orders`. Current counts: items=169, vendors=41, customers=37, sales_orders=10 (vs Plan 01 baseline of 109/5/8/4).
- **Fix:** Switched CHECK A's `data_signals` assertions from `==` to `>=`: `item_count >= 109`, `vendor_count >= 5`, `customer_count >= 8`, `so_count >= 4`, `brand_count >= 4`. Added comment explaining pre-existing pollution is out of scope per GSD scope rule.
- **Files modified:** `scripts/smoke-onboarding.sh`
- **Commit:** `b4224df`

**4. [Rule 3 - Blocking] sample-data 5xx classified as FAIL, contradicting Quick-338's documented YELLOW posture**
