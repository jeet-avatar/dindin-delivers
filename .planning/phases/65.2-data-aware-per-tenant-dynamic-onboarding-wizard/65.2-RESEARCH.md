## Summary

This phase replaces the abstract 5-question wizard at `/onboarding/recommend.html` with one that (a) introspects what the tenant has already imported, (b) loads per-tenant question SETS and pre-filled ANSWERS so the workspace feels custom from first paint, and (c) drives recommendations from real signals (item count, brand breakdown, sales-order count + total, BOM parts, vendors, customers, corporate facts) rather than abstract categories alone.

The existing surface is solid: `withTenantClient` + `auditLog` + `requireRole` + `requireAuth` + `tenantContext` are all production-tested (Phase 55 RLS, Phase 59 audit_log_v2). Migration cadence is at 037 (Phase 65-01's `turion.parts` was the most recent). Phase 56 (Stripe) is paused so 038 is free. The data backbone exists: `turion.items.source_data->>'brand'` already encodes brand info, item IDs are brand-prefixed (`SOLO-`, `ORU-`, `ISLE-`, `CHUB-`), and `data/solobrands-corporate.json` is a static file served at `/data/solobrands-corporate.json`.

**Primary recommendation:** Add ONE new table (`public.tenant_onboarding_profile`), ONE new tenants column (`tenants.corporate_data jsonb`), TWO new endpoints (`GET /api/onboarding/profile` + `PATCH /api/onboarding/profile`), ONE new pure helper (`buildDataSignals(client, tenantId)`), ONE new JSON catalog (`backend/src/onboarding/question-sets.json`), and ONE rewrite of `/onboarding/recommend.html` to fetch+prefill+autosave. Use migration 038 (037 was Phase 65-01 parts; 037 collision-free). Seed Solo Brands + turion + brandmonkz + dollor in the same migration with `source='seeded'`.

1. **Where corporate_data lives** — recommend `public.tenants.corporate_data jsonb DEFAULT NULL` column over a separate `tenant_corporate_data` table. CREATE TABLE IF NOT EXISTS public.tenant_onboarding_profile (
  tenant_id            uuid PRIMARY KEY REFERENCES public.tenants(id) ON DELETE CASCADE,
  question_set_code    text NOT NULL CHECK (question_set_code IN ('d2c-multibrand','aerospace-hardware','services-saas')),

  signals_computed_at  timestamptz,

ALTER TABLE public.tenant_onboarding_profile ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.tenant_onboarding_profile FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON public.tenant_onboarding_profile

  USING      (tenant_id = current_setting('app.tenant_id', true)::uuid)

// Source: extend backend/src/routes/onboarding.ts following lines 188-216 (/state pattern)
r.get('/profile', async (req: Request, res: Response) => {
  try {
    const result = await withTenantClient(req, async (client) => {
      // Load profile row (returns null if not yet seeded — shouldn't happen post-mig-038)
      const p = await client.query<{
        question_set_code: string;
        answers: any;
        source: string;
        data_signals_cached: any;
        signals_computed_at: string | null;
      }>(
        `SELECT question_set_code, answers, source, data_signals_cached, signals_computed_at
           FROM public.tenant_onboarding_profile`,
      );
      let signals = p.rows[0]?.data_signals_cached ?? null;
      const stale = !p.rows[0]?.signals_computed_at
        || (Date.now() - new Date(p.rows[0].signals_computed_at).getTime() > 5 * 60_000);
      if (stale) {
        signals = await buildDataSignals(client, req.tenant!.id);
        await client.query(
          `UPDATE public.tenant_onboarding_profile
              SET data_signals_cached = $1::jsonb,
                  signals_computed_at = now()`,
          [JSON.stringify(signals)],
        );
      }
      // Load corporate_data from tenants (read-only here).
      const t = await client.query<{ corporate_data: any }>(
        `SELECT corporate_data FROM public.tenants WHERE id = $1`,
        [req.tenant!.id],
      );
      return {
        profile: p.rows[0] ?? null,
        signals,
        corporate_data: t.rows[0]?.corporate_data ?? null,
      };
    });
    const code = result.profile?.question_set_code ?? 'd2c-multibrand';

### Pattern 3: PATCH /api/onboarding/profile (partial deep-merge + audit)

// Source: extend backend/src/routes/onboarding.ts following lines 221-244 (/checklist pattern + finalize audit)
r.patch('/profile', requireRole('admin', 'manager'), async (req: Request, res: Response) => {
  const patch = req.body?.answers;
  if (!patch || typeof patch !== 'object' || Array.isArray(patch)) {
    res.status(400).json({ error: 'answers object required' });
    return;
  }
  // Light validation — keys are known wizard slugs.
  const ALLOWED_KEYS = new Set(['industry','team_size','pain_point','tools_today','asc606_needs']);
  for (const k of Object.keys(patch)) {
    if (!ALLOWED_KEYS.has(k)) {
      res.status(400).json({ error: `Unknown answer key: ${k}` });
      return;
    }
  }
  try {
    await withTenantClient(req, async (client) => {
      const before = await client.query<{ answers: any; source: string }>(
        `SELECT answers, source FROM public.tenant_onboarding_profile`,
      );
      // jsonb || jsonb does shallow merge — perfect for autosave-per-click.
      await client.query(
        `UPDATE public.tenant_onboarding_profile
            SET answers = answers || $1::jsonb,
                source = 'user',
                updated_at = now()`,
        [JSON.stringify(patch)],
      );
      await auditLog(req, client, {
        action: 'onboarding.profile_updated',
        resource_type: 'tenant_onboarding_profile',
        resource_id: req.tenant!.id,
        before: before.rows[0] ?? null,
        after: { answers_patch: patch, source: 'user' },
      });
    });
    res.json({ ok: true });
  } catch (e: unknown) {
    const msg = e instanceof Error ? e.message : String(e);
    console.error('[PATCH /api/onboarding/profile] error:', msg);
    res.status(500).json({ error: 'Profile update failed' });
  }
});

### Pattern 4: `buildDataSignals` (pure read, 6 queries in one txn)

```typescript
// NEW file: backend/src/onboarding/data-signals.ts
import type { PoolClient } from 'pg';

export interface DataSignals {
  item_count: number;
  brand_breakdown: Record<string, number>;  // { "solo-stove": 32, "oru-kayak": 22, ... }
  so_count: number;
  so_total_usd: number;
  bom_part_count: number;
  vendor_count: number;
  customer_count: number;
  has_corporate_facts: boolean;
}

export async function buildDataSignals(client: PoolClient, _tenantId: string): Promise<DataSignals> {
  // All queries run inside the caller's withTenantClient txn —
  // RLS guarantees they only see this tenant's rows.
  const [items, brands, sos, parts, vendors, customers, corp] = await Promise.all([
    client.query<{ c: string }>(`SELECT count(*)::text AS c FROM turion.items`),
    client.query<{ brand: string; c: string }>(
      `SELECT (source_data->>'brand') AS brand, count(*)::text AS c
         FROM turion.items WHERE source_data ? 'brand'
         GROUP BY (source_data->>'brand')`
    ),
    client.query<{ c: string; t: string }>(
      `SELECT count(*)::text AS c, COALESCE(sum(total),0)::text AS t FROM turion.sales_orders`
    ),
    client.query<{ c: string }>(`SELECT count(*)::text AS c FROM turion.parts`),
    client.query<{ c: string }>(`SELECT count(*)::text AS c FROM turion.vendors`),
    client.query<{ c: string }>(`SELECT count(*)::text AS c FROM turion.customers`),
    client.query<{ has: boolean }>(
      `SELECT (corporate_data IS NOT NULL) AS has FROM public.tenants WHERE id = current_setting('app.tenant_id')::uuid`
    ),
  ]);
  const brand_breakdown: Record<string, number> = {};
  for (const r of brands.rows) brand_breakdown[r.brand] = parseInt(r.c, 10);
  return {
    item_count:        parseInt(items.rows[0]?.c ?? '0', 10),
    brand_breakdown,
    so_count:          parseInt(sos.rows[0]?.c ?? '0', 10),
    so_total_usd:      parseFloat(sos.rows[0]?.t ?? '0'),
    bom_part_count:    parseInt(parts.rows[0]?.c ?? '0', 10),
    vendor_count:      parseInt(vendors.rows[0]?.c ?? '0', 10),
    customer_count:    parseInt(customers.rows[0]?.c ?? '0', 10),
    has_corporate_facts: !!corp.rows[0]?.has,
  };
}
```

### Anti-Patterns to Avoid

- **Multi-table writes outside `withTenantClient`** — every write must be inside ONE transaction with `SET LOCAL app.tenant_id`. Phase 55 RLS will REJECT writes from the `zietra_app` role otherwise. See db.ts:55-80.
- **`Host` header to APIGW** — proven broken by Quick 338 (line 105 of smoke-onboarding.sh). APIGW SNI returns 403. Use `X-Tenant-Slug` only.
- **Trust the JWT for tenant context** — `tenantContext` reads `X-Tenant-Slug` header (NOT the JWT). The same Cognito user can belong to multiple tenants. See middleware/tenant.ts:57.
- **Compute signals on every GET without cache** — 6 SQL queries × every keystroke autosave = melts Aurora. Always check `signals_computed_at` first.
- **Skip the audit log** — every PATCH MUST call `auditLog(req, client, ...)` inside the same `withTenantClient` callback (Phase 59-01 requirement).
- **Inline a `<style>` block with hardcoded brand colors** — use the `--z-*` CSS variables already in `/app-shell.css` (e.g. `--z-primary`, `--z-text-1`, `--z-border`). Verified in recommend.html lines 14-74.
- **Add a frontend `<script>` to load corporate-data.json directly from the static URL** — instead, serve it via `GET /api/onboarding/profile` so the wizard sees the same RLS-gated view as the backend rule engine. (The static file approach leaks corporate intel of other tenants if they ever exist.)

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Tenant-scoped DB query | Manual `WHERE tenant_id = ...` | `withTenantClient(req, async client => ...)` from `backend/src/db.ts` | RLS auto-enforced via `SET LOCAL app.tenant_id`. Manual filter is bypassable. |
| Audit logging | `INSERT INTO audit_log_v2` directly | `auditLog(req, client, opts)` from `backend/src/db.ts:111` | Handles tenant_id + actor sub + IP (CloudFront-aware) + UA truncation. |
| Cognito role check | Decode JWT in handler | `requireRole('admin', 'manager')` from `middleware/role.ts:49` | 60s cache + DB fallback + 403 JSON. |
| Tenant slug → id | `pool.query('SELECT id FROM tenants ...')` in handler | `tenantContext` middleware → `req.tenant.id` | 60s positive + 5s negative cache; 400 if missing header, 404 if unknown. |
| Frontend HTTP client | `fetch(...)` direct | `window.erpApi.get / post / patch / delete` (from `/erp-api.js`) | Adds `Authorization: Bearer <IdToken>` + `X-Tenant-Slug` header automatically. Verified at recommend.html line 206, 254. |
| Frontend tenant resolution | Parse hostname | `window.cognitoAuth.requireSession()` at page top | Standard pre-auth gate; matches every other page. Verified at recommend.html line 10. |
| jsonb deep merge in SQL | Manual JSON.parse + JSON.stringify round-trip | Postgres `jsonb || jsonb` operator | Shallow merge; perfect for `{team_size: '201-1000'}` partial PATCH. |
| Question-set storage | Postgres table + RLS + grants + cache invalidation | `import QUESTION_SETS from './question-sets.json'` (loaded once at cold start) | Mirror of `recommend-rules.json` — pure data, version-controlled, zero round-trip. |
| Idempotent re-run guard for seeds | Manual SELECT-then-INSERT | `INSERT ... ON CONFLICT (tenant_id) DO NOTHING` | Standard Postgres idiom; Phase 65-01 uses ON CONFLICT throughout. |

**Key insight:** every helper this phase needs ALREADY EXISTS. The phase is glue + one new table + one new JSON file + a frontend rewrite. No new infra, no new IAM, no new secrets, no new Lambda.

## Common Pitfalls

### Pitfall 1: Cross-tenant leak via wrong scoping (RLS context not set)

**What goes wrong:** A new endpoint forgets `withTenantClient` and uses `pool.query` directly → RLS check fails (or worse, with `zietra_admin` role, returns ALL tenants' rows).

**Why it happens:** Copy-pasting from a route that uses `pool.query` directly for unauthenticated paths (e.g. `/api/tenants/signup` at line 66, 117).

**How to avoid:** Every route file MUST start with `r.use(tenantContext, requireAuth)` AND every DB call inside a handler MUST use `withTenantClient(req, async client => await client.query(...))`. Verified in `backend/src/routes/onboarding.ts:25` already does this.

**Warning signs:** Postgres errors `unrecognized configuration parameter "app.tenant_id"` in CloudWatch — proves a query ran OUTSIDE `withTenantClient`. Phase 55 made this loud-fail intentionally.

### Pitfall 2: Stale prefilled answers after data refresh

**What goes wrong:** Solo Brands' data is wiped + re-imported (e.g. Phase 65-01's wipe.sql), but `data_signals_cached` still shows the old `item_count: 15`.

**Why it happens:** The 5-min TTL on `signals_computed_at` is fine for human-pace edits but bad for batch data-refresh events.

**How to avoid:** Support `?refresh=true` on `GET /api/onboarding/profile` to force a recompute. Document in the smoke harness so post-import calls always pass it.

**Warning signs:** Wizard shows "We see 15 items" but `/netsuite/items` shows 109. Smoke matrix should catch this.

### Pitfall 3: Cold-start cost of 6 queries in `buildDataSignals`

**What goes wrong:** First request after a Lambda cold start takes 400-800ms because 6 sequential queries are wrapped in `Promise.all` but the txn BEGIN + 6 round-trips ≈ 7 × RDS-Proxy hops.

**Why it happens:** Even with `Promise.all`, the connection pool has only 1 client per `withTenantClient` invocation, so queries serialize on the same client.

**How to avoid:** ONE option — collapse all 6 queries into a single `SELECT ... FROM (VALUES) CROSS JOIN LATERAL (SELECT ...)` mega-query. Faster, but harder to read. Recommend: keep the 6-query shape (clear + maintainable) and rely on the 5-min cache to make this a once-per-tenant-per-5-min cost. Cold-start hit is <1s.

**Warning signs:** CloudWatch p99 latency on `GET /api/onboarding/profile` >1s. Add the cache from day 1.

### Pitfall 4: `corporate_data` NULL for tenants that didn't get Phase 65-01 treatment

**What goes wrong:** Logging in as turion/brandmonkz/dollor, the wizard tries to render "Based on FY25 corporate facts…" and dereferences `null.industry`.

**Why it happens:** Only Solo Brands has `corporate_data` populated. Migration 038 should backfill ALL 4 tenants with at least a minimal stub.

**How to avoid:** Migration 038 INSERT seeds ALL 4 tenants into `tenant_onboarding_profile`. For `corporate_data`, leave NULL for non-solobrands tenants and the GET endpoint returns `has_corporate_facts: false` + `corporate_summary: null`. Frontend renders the signals strip conditionally: `if (data.corporate_summary) { ... } else { ... }`.

**Warning signs:** TypeError in browser console on turion.zietra.com/onboarding/recommend. Smoke harness must visit all 4 tenants, not just solobrands.

### Pitfall 5: Module-code mismatch between recommendation engine and `tenant_features` CHECK constraint

**What goes wrong:** Recommendation engine emits `'inventory'` or `'projects'` (which the prompt mentioned), but the CHECK constraint at migration 024 line 27-29 only allows 13 specific codes. `/api/onboarding/finalize` rejects with `500`.

**Why it happens:** The prompt's 9-module list `[crm, sales, items, plm, asc606, ai-agents, purchase, inventory, projects]` includes non-existent codes. The real Solo Brands `tenant_features` enabled set is `[ai-agents, crm, items, lean-erp-pro, mes, plm, purchase, quality, sales]` (Quick 338 BEFORE snapshot).

**How to avoid:** Cross-check the test `RecommendationEngineDataDriven`: assert recommendation list ⊆ `ALL_MODULES` (the 13-code set at rule-engine.ts:46-49). Plan task MUST verify the Solo Brands expected output matches Quick 338's BEFORE snapshot exactly.

**Warning signs:** `tenant_features CHECK constraint violated` in CloudWatch on a /finalize call.

### Pitfall 6: Migration numbering collision with Phase 56 (Stripe, paused)

**What goes wrong:** Plan uses 037 for the new table; Phase 65-01 already used 037 for `turion.parts`. Or plan uses 038, but Phase 56 had reserved 037+ when it was paused.

**Why it happens:** Multiple parallel phases vying for the next free migration number.

**How to avoid:** Verified `ls backend/migrations/` last entry is `037_create_turion_parts.sql`. Use **038**. Phase 56 was paused at "Wave 1 Task 2" with no migration shipped (per handoff line 36) — `037` reservation was theoretical. If Phase 56 resumes, it takes 039+.

**Warning signs:** `git pull` shows a 038 file from another branch. Mitigate via Phase 56 status check before running migration.

### Pitfall 7: `requireRole('admin')` blocks legitimate `/profile` GET for tenant members

**What goes wrong:** Member-tier users (not admin/manager) cannot LOAD the wizard.

**Why it happens:** If we mirror `/finalize` and gate GET behind `requireRole('admin')`, every non-admin gets 403.

**How to avoid:** GET `/profile` should be open to ANY authenticated tenant member (the existing `r.use(tenantContext, requireAuth)` at line 25 is enough — no `requireRole` on GET). PATCH `/profile` should require `admin` or `manager` (mirrors `/checklist` at line 221). FINAL `/finalize` is already admin-only (line 45).

**Warning signs:** Non-admin user opens `/onboarding/recommend` and sees a 403 banner instead of the wizard.

### Pitfall 8: Frontend autosave debouncing leaks stale answers

**What goes wrong:** User clicks Q1=`aerospace`, then immediately Q1=`d2c-multibrand`. Both PATCH requests fire; the second arrives FIRST due to network jitter. Final state = `aerospace`.

**Why it happens:** Naive `setTimeout(patchFn, 400)` per click without cancellation.

**How to avoid:** Use a debounced send: `clearTimeout(pendingPatch); pendingPatch = setTimeout(() => fetch(...), 400)`. Or use a per-key version monotonic counter — PATCH only succeeds if its version is the latest. Recommend debounce-only (simpler; collision window is the 400ms typing-pause).

**Warning signs:** User says "I picked D2C but it saved as Aerospace." Smoke harness can't catch this — needs manual test.

### Pitfall 9: Pre-auth populator pattern (Phase 63 lesson)

**What goes wrong:** Adding a new `data-z-*` attribute to `recommend.html` works on most pages because `app-shell.js` populates it post-auth. But the page is RENDERED before auth completes.

**Why it happens:** `<script src="/cognito-auth.js"></script>` followed by `(async () => { await cognitoAuth.requireSession(); })();` runs async — the DOM renders the empty span first.

**How to avoid:** This page already loads `app-shell.js` (line 13) AND calls `requireSession()` before rendering. The dynamic wizard content can wait for `await window.cognitoAuth.requireSession()` to resolve before fetching `/api/onboarding/profile`. The pre-auth `data-z-tenant-name` populator pitfall does NOT apply because this page is fully post-auth.

**Warning signs:** Visible `[tenant-name]` placeholder in screenshot before populator runs. Not applicable to this phase but flagged for completeness.

### Pitfall 10: Smoke harness skips Solo Brands restore

**What goes wrong:** Smoke leaves Solo Brands' profile in a mutated state — next time a real demo runs, the wizard shows the test answers.

**Why it happens:** Smoke happily PATCHes but forgets to PATCH-back to seeded baseline.

**How to avoid:** Mirror Quick 338's discipline exactly (SUMMARY.md lines 105-115): BEFORE snapshot → mutate → AFTER snapshot → diff → RESTORE → snapshot diff against BEFORE → assert byte-equal. Use the same `zietra-rls-runner-55-05` Lambda probe used in `smoke-solobrands.sh`.

**Warning signs:** Operator opens solobrands.zietra.com next day and sees `team_size: solo` (from a smoke test) instead of `201-1000`.

1. **Should `tenant_users.role` be used for the GET gate or just tenant membership?**

3. **Should `corporate_data` be writeable by an admin endpoint this phase, or read-only?**

   - What's unclear: how is `corporate_data` populated for new tenants signing up (e.g. someone signs up at brandmonkz today — corporate_data is NULL forever unless someone runs SQL)?

   - What we know: One row per tenant; PK is `tenant_id`. UPDATE always works (no concurrent inserts).
